# 学院行政办助理排班系统

## 软件需求规格说明书

---

## 1 引言

### 1.1 编写目的

本文档为"学院行政办助理排班系统"的软件需求规格说明书，旨在明确系统的功能需求、非功能需求、数据需求和接口需求，为后续的系统设计、编码实现和测试验收提供依据。本文档的读者包括项目负责人、软件开发人员、测试人员及课程指导教师。

### 1.2 项目背景

学院行政办公室每学期需安排学生助理协助处理日常行政事务。助理来源为学生群体，涵盖本科生和研究生，各自课程安排不同，空闲时间各异。传统的人工排班方式效率低、易出错，且难以兼顾各类约束条件（如每人最短/最长上班时间、同时段排班人数限制等）。为此，设计本排班系统，通过信息化手段实现排班自动化，提高排班效率与准确性。

### 1.3 术语定义

| 术语 | 定义 |
|------|------|
| 助理 | 指被安排在行政办协助处理事务的学生，包括本科生和研究生 |
| 排班 | 指将助理分配到具体时间段的工作安排过程 |
| 课程表 | 指学生个人的课程安排，包含课程名称、时间、周次、教室等信息 |
| 排班表 | 指最终的助理工作安排结果，展示每位助理在各时间段的值班情况 |
| 约束条件 | 指排班过程中必须满足的限制规则，如最短/最长工作时间、同时段人数限制等 |
| 自动排班 | 指系统根据预设规则和助理课程表自动计算最优排班方案的功能 |

## 2 项目概述

### 2.1 项目目标

本项目的目标是开发一个**单机桌面排班系统**，实现学院行政办助理排班的自动化和规范化。具体目标包括：

1. 支持学生课程表的导入与解析，自动识别助理的空闲时间段；
2. 根据预设排班规则和约束条件，自动完成助理排班；
3. 提供手动调整功能，允许管理员对自动排班结果进行微调；
4. 支持排班表的导出（如Excel格式），便于打印和分发；
5. 提供助理个人信息管理和课程表管理功能。

### 2.2 系统架构概述

本系统为**单机桌面应用**（Windows 平台，经 Tauri v2 打包），不依赖后端服务器，所有数据保存在本机。系统整体架构分为以下层次：

1. **表现层**：基于 Vue 3 + Element Plus 的图形界面，以 Tauri WebView 窗口呈现，提供课程表导入、排班查看、手动调整等操作入口；
2. **业务逻辑层**：实现排班算法（贪心启发式）、约束校验、数据管理等核心业务逻辑；
3. **数据层**：使用浏览器本地数据库 IndexedDB（经 Dexie.js 封装），存储助理信息、课程表数据、排班规则配置、排班结果及操作日志等数据。

> 技术选型的完整决策过程见 `docs/ADR-001.md`（存储与打包）与 `docs/ADR-002.md`（框架、算法与撤销机制）。

### 2.3 用户特征

本系统的主要用户为学院行政办公室的工作人员（排班管理员）。用户应具备基本的计算机操作能力，无需专业的编程知识。系统界面应简洁直观，操作流程清晰。

### 2.4 假设与依赖

1. 假设学院已提供标准化的学生课程表文件格式；系统导入以本项目提供的**标准 Excel 模板**为准，Word 格式的原始课程表需先转换为 .xlsx（附转换指引）；
2. 假设助理人数在合理范围内（不超过50人），系统性能可满足实时排班需求；
3. 依赖运行环境：Windows 10 及以上系统（自带 WebView2 渲染引擎）。

## 3 功能需求

### 3.1 自动排班功能（F01）

系统应能根据以下输入自动完成排班：

- **输入**：所有助理的课程表数据、排班规则配置、排班时间段设置；
- **处理**：系统识别每位助理的课程空闲时间，结合排班约束条件（每人最短/最长工作时间、同时段人数限制等），采用**贪心启发式排班算法**自动分配助理到各时段（算法选型与流程见 ADR-002 第三节）；
- **输出**：生成初始排班表，展示每位助理在各时间段的值班安排。

**优先级：高。** 这是系统的核心功能，应优先实现。

### 3.2 助理信息管理功能（F02）

系统应提供助理个人信息的录入、查看、修改和删除功能。助理信息字段包括：

1. **姓名**：助理的真实姓名；
2. **学号**：学院统一学号；
3. **身份类型**：本科生/研究生（不同身份可能对应不同的排班规则）；
4. **联系电话**：手机号码；
5. **QQ号**：用于即时通讯联系；
6. **班级**：所属班级信息；
7. **课程表文件**：上传该助理的个人课程表文件。

> 2026-09-11 增补：课程表导入时若解析出的学生（姓名+学号）在系统中不存在，系统应支持**按学生信息一键创建助理**，身份由课程条目标记（（本）/（研））自动推导，创建后自动选为导入归属。

### 3.3 排班规则配置功能（F03）

系统应允许管理员配置以下排班规则：

1. **每人最短上班时间**：设置每位助理在一个排班周期内最少需要值班的小时数/天数；
2. **每人最长上班时间**：设置每位助理在一个排班周期内最多可以值班的小时数/天数；
3. **同时段排班人数要求**：设置同一时间段内最少和最多需要多少名助理值班；
4. **排班原则**：可配置排班优先级策略（如按身份类型优先、按空闲时间优先、轮询分配等）；
5. **排班周期**：设置排班覆盖的周次范围（如第1周至第17周）；
6. **上班时间表**（2026-09-11 增补）：设置每周工作日（默认周一至周五）与上班节次（默认上午第 1~4 节、下午第 8~11 节）；排班只发生在工作日的上班节次内，**排班时段按单节划分**（第 1 节、第 2 节……各自为独立排班时段）并按节次显示；
7. **排班模式**（2026-09-11 增补）：可选择"各周独立排班"（按每周课程占用分别计算）或"各周排班相同"（以整个周期内任一周有课即视为占用，生成一份排班后复制到全部周次——导出时仅需单周表）；
8. **课程占用过滤**（2026-09-11 增补）：可选择理论课（样例标记（本）/（研））与实验课（标记（实））是否计入值班占用。

### 3.1 补充（2026-09-11）：一次性完成全周期排班

F01 应支持**按排班周期一次性生成全部周次的排班方案**：逐周根据该周课程占用计算可用性；"各周排班相同"模式下生成一份方案并复制到周期内所有周次。写入时按周落库。

### 3.4 手动调整功能（F04）

系统应提供手动调整排班结果的能力：

1. 管理员可手动将某位助理分配到指定时间段；
2. 管理员可移除某位助理在指定时间段的值班安排；
3. 手动调整后系统应自动校验是否违反已配置的排班约束条件，并在违反时给出警告提示；
4. 支持排班记录的撤销/重做操作（采用**快照栈**机制实现，见 ADR-002 第四节）。

### 3.5 数据导入导出功能（F05）

系统应提供数据的导入和导出能力：

1. **课程表导入**：支持批量导入学生课程表文件（按标准 Excel 模板填写），系统自动解析并录入；Word 格式（.doc/.docx）不直接支持，需先转换为 .xlsx；
2. **排班表导出**：支持将最终排班结果导出为Excel文件，便于打印和线下分发；
3. 导出内容应包括：日期、时间段、值班助理姓名、联系方式等关键信息。

### 3.6 课程表管理功能（F06）

系统应提供课程表的查看和管理能力：

1. 允许管理员手动修改某位助理的课程表（如课程时间临时调整）；
2. 支持查看任意助理的课程表详情；
3. 课程表修改后，系统应提示是否需要同步更新排班结果。

### 3.7 排班表模板管理功能（F07）

系统应提供排班表和课程表模板的配置管理：

1. 可设置和修改空白排班表的格式模板（如表头字段、时间段划分、列宽等）；
2. 可设置和修改课程表导入模板的格式，以适配不同学期或不同格式的课程表文件；
3. 模板修改后，新导入的数据将自动按新模板格式展示。

### 3.8 重新排班功能（F08）

当新增助理或排班规则发生变更时，系统应支持重新执行排班算法：

1. 新增助理后，可选择对现有排班表进行增量调整或全量重新排班；
2. 重新排班时保留已手动调整且未冲突的安排（通过排班记录的来源标记区分），仅对未分配或冲突的时段重新计算；
3. 提供排班结果对比功能，基于重排前后的排班快照差异实现（见 ADR-002 第四节）。

## 4 非功能需求

### 4.1 性能需求

1. 系统应在5秒内完成一次完整排班计算（助理人数<=50人时）；
2. 课程表导入解析应在3秒内完成（单文件）；
3. 页面响应时间不超过2秒。

### 4.2 安全性需求

1. 系统为单机本地应用，不设登录认证，通过操作系统账户权限与本机物理接触控制访问；
2. 助理的联系电话、QQ号等个人信息仅存储于本机；导出的排班表包含联系方式时，系统应提示用户妥善保管文件；
3. 排班数据的修改应记录操作日志（本地存储），便于追溯。

### 4.3 可用性需求

1. 系统界面应简洁友好，操作步骤不超过3步即可完成常见操作；
2. 系统应提供操作提示信息，帮助用户理解当前操作状态；
3. 应用以独立桌面窗口运行（Tauri + WebView2），要求 Windows 10 及以上系统。

### 4.4 可维护性需求

1. 源代码应编写清晰的注释，遵循统一的编码规范；
2. 系统架构应模块化，各功能模块之间耦合度低，便于独立修改和扩展；
3. 应提供配置文件管理排班规则，避免硬编码。

## 5 数据需求

### 5.1 课程表数据结构

课程表数据是系统排班的基础输入。根据标准课程表样例，每门课程包含以下信息：

1. **课程编号**：如"10125121047"，用于唯一标识课程；
2. **课程名称**：如"软件工程[02]"；
3. **上课周次**：如"1-4周"、"6-17周"，表示课程生效的周次范围；
4. **上课节次**：如"第一节-第二节"、"第三节-第五节"等；
5. **上课星期**：星期一至星期日；
6. **上课教师**：授课教师姓名；
7. **上课地点**：如"南院-博学东楼-303"。

### 5.2 排班表数据结构

排班表是系统的核心输出，包含以下信息：

1. **日期/周次**：排班覆盖的具体周次；
2. **时间段**：如"第一节-第二节"、"第三节-第五节"等；
3. **值班助理**：被安排到该时段的助理姓名及学号；
4. **值班地点**：行政办公室位置；
5. **备注**：特殊情况说明。

### 5.3 助理信息数据结构

助理信息表包含以下字段：

| 字段名 | 类型 | 约束 |
|--------|------|------|
| 助理ID | 字符串 | 系统内部唯一标识 |
| 姓名 | 字符串 | 非空 |
| 学号 | 字符串 | 唯一 |
| 身份类型 | 枚举值 | 本科生/研究生 |
| 手机号 | 字符串 | 格式校验 |
| QQ号 | 字符串 | - |
| 班级 | 字符串 | - |
| 关联课程表文件路径 | 字符串 | - |

## 6 接口需求

### 6.1 用户界面

系统以桌面窗口（Tauri WebView）作为用户界面，主要页面包括：

1. **仪表盘**：展示排班概览、待办事项等；
2. **助理管理页面**：助理信息的增删改查；
3. **课程表管理页面**：课程表导入、查看、修改；
4. **排班配置页面**：排班规则设置；
5. **排班表页面**：自动排班执行、手动调整、排班结果查看与导出。

### 6.2 文件接口

1. **课程表导入接口**：接受按标准格式填写的 Excel 文件（.xlsx，由学院原始 Word 课程表转换而来，格式定义见附录A），系统自动解析；.doc/.docx 等 Word 格式不直接解析，需先转换为 .xlsx（附转换指引）；
2. **排班表导出接口**：输出标准 Excel 格式文件（.xlsx），包含格式化的排班表格。

### 6.3 数据库接口

系统使用浏览器本地数据库 IndexedDB（经 Dexie.js 封装）存储结构化数据，包括助理信息表、课程表数据表、排班规则配置表、排班结果表、操作日志表、排班快照表等，不使用服务器端数据库。选型依据见 ADR-001。

## 7 附录

### 附录A：标准课程表样例说明

学院原始课程表样例为 Word 格式（`timeTableForStu12.doc`），转换后的 `timeTableForStu12.xlsx`（位于项目根目录）作为系统导入的实际输入格式。其结构要点如下（已实际核验）：

1. **表头区**：第 1 行为标题"我的课程表"；第 2 行含学期信息（如"2026-2027-1"）与学生姓名和学号（如"学生：庞士豪(1024005228)"）；
2. **特殊信息区**："上课时间暂未确定的课程"与"调课信息"以自由文本形式出现在网格上方，解析时应跳过并标记提示；
3. **网格区**：列为"节次/星期"与星期一至星期日（共 9 列），行为节次段（如"第一节-第二节"、"第三节-第五节"）；
4. **课程单元格**：为多行文本，格式为"（身份）课程编号-课程名称[班次]"换行后接周次信息（如"1-4周"、"10周"）；
5. **合并单元格**：跨节次/跨节的课程以合并单元格表达（样例含 65 个合并区域），解析时需按合并范围展开。

**解析实现要求**：处理合并单元格展开、单元格内多行文本拆分、周次范围解析（如"1-4周"、"10周"、"5-17周单周"等变体），并对无法解析的单元格给出行级错误提示。
