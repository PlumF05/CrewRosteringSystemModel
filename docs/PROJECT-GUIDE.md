# CRSM 项目指导书（初学者版）

> 目标读者：懂一点后端（数据库、事务、HTTP），但**几乎没写过前端**的你。
> 读法：第 1~3 章建立全貌 → 第 4~5 章逐流程跟代码 → 第 6~8 章理解设计思想与逐文件导读。
> 所有代码引用都是真实路径与真实行为，可边读边打开对照。术语见 [GLOSSARY](../GLOSSARY.md)。

## 1. 这个项目是什么

学院行政办公室每学期要给几十名学生助理排值班表。手工排要避开每个人的上课时间、兼顾人数和工时公平，非常繁琐。本系统把它自动化：

```
导入学生课表(Excel) → 一键生成 17 周值班方案 → 手动微调 → 写入 → 导出带格式的 Excel 排班表
                                                              ↘ 备份/换机交接（一个 JSON 文件）
```

它是 **Windows 离线桌面应用**：没有服务器、没有账号、不联网——所有数据存在本机浏览器的 IndexedDB 数据库里，由 Tauri 把网页"装进"一个桌面窗口。

## 2. 技术栈白话解释（后端类比版）

| 技术 | 是什么 | 后端类比 |
|---|---|---|
| **Vue 3** | 前端界面框架。写"组件"（.vue 文件 = 模板 + 脚本 + 样式三段），数据变了界面自动变 | 类似模板引擎 + 自动重新渲染的 JSP/Thymeleaf |
| **TypeScript** | 带类型的 JavaScript，编译期查错 | 就是 Java/C# 的类型系统移植到 JS |
| **Vite** | 开发服务器 + 打包器 | 类似 spring-boot-devtools 热重载 + Maven package |
| **Element Plus** | 现成 UI 组件库（按钮/表格/弹窗） | 类似 Bootstrap，但组件是"活的" |
| **Vue Router** | 页面切换（URL → 组件），单页应用不刷新 | 类似后端路由表，但分发到组件而非 Controller |
| **Pinia** | 跨组件共享状态的库（本项目装了暂未用，页面内状态用 `ref` 即可） | 类似会话级 Bean |
| **Dexie** | IndexedDB 的封装（IndexedDB 是浏览器内置的本地 NoSQL 数据库） | 类似一个轻量 ORM，支持事务 |
| **Web Worker** | 后台线程。排班计算放进去，界面不卡、可取消 | 类似独立线程池任务，靠消息通信 |
| **Tauri** | 把网页打包成桌面 exe（用系统自带的 WebView 渲染） | 类似 Electron 但用系统浏览器内核，体积小 |
| **xlsx-js-style** | 读写 Excel 文件（支持单元格样式） | 类似 Apache POI |

## 3. 跑起来与目录结构

```bash
npm ci            # 安装依赖（= mvn install）
npm run dev       # 浏览器开发模式 http://localhost:1420
npm test          # 304 项测试（Vitest）
npm run build     # 类型检查 + 打包到 dist/
npm run tauri dev # 桌面窗口开发模式
```

```
src/
├─ algorithms/   算法层（★纯函数：不 import Vue/Dexie，Node 里可直接测试）
├─ db/           数据层（仓储 + 各业务服务：事务/版本/校验都在这）
├─ workers/      排班计算线程
├─ templates/    导入/导出模板管理
├─ views/        页面（路由懒加载：进哪个页才下载哪个页的代码）
├─ components/   从大页面拆出的组件（手调对话框/快照卡片）
├─ utils/        工具（课表解析/周次解析/节次轴/导出）
└─ layouts/      侧边栏 + 顶栏骨架
```

**一条铁律**（分层纪律）：

```
views（页面）→ db/业务服务 → repositories（仓储）→ Dexie（IndexedDB）
                     ↘ algorithms（纯函数）
```

页面永远不直接写数据库；算法永远不知道有界面。找不到一个反例——这是刻意的，好处是每层都能独立测试。

## 4. 数据模型：七张表（`src/db/schema.ts` + `src/db/database.ts`）

| 表 | 存什么 | 关键设计 |
|---|---|---|
| `assistant` 助理 | 姓名、学号（**唯一索引**）、身份、电话/QQ、个性化节数覆盖、**课表状态**（ready/confirmed_empty/needs_review，缺省=未导入） | "账号"与"助理"不分家——单机无登录 |
| `course` 课程 | 助理id、课程名、类别、星期、**节次原文**（如"第三节-中课2"）、周次区间 | 节次存原文不存数字——数字+中课/晚课混排，原文是唯一真相 |
| `duty_schedule` 排班 | 周、星期、时段(c{节号})、助理id、来源(auto/manual)、**locked 锁定**、**短段例外原因** | 复合唯一索引：同周同时段同人不可重复（数据库层兜底） |
| `config` 配置 | 键值对：排班规则 rules、模板 templates、**dataRevision 业务版本**、撤销日志 adjustJournal | JSON 结构化存储 |
| `operation_log` 操作日志 | 谁在何时做了什么 | 追溯用 |
| `schedule_snapshot` 命名快照 | 整份排班 + **当时规则与人员名单（meta）** | 自包含：删人改规则后历史不坏 |
| `recovery_backup` 恢复副本 | 恢复备份前的当前数据 | 独立表隔离，最多留 5 份 |

**schema 版本迁移**（database.ts v1→v4）：Dexie 按版本号顺序执行 upgrade。v2/v3 各有"清空前归档"的历史故事（注释里写了为什么不能逐行平移节次键——会撞唯一索引）；v4 只是加表不动数据。**加非索引字段不需要升版本**（如 locked），只有加表/加索引才要。

## 5. 六大业务流程逐条跟代码

### 5.1 导入一份课表（原子性 + 自动归档）

文件：`src/views/CoursesView.vue` → `src/db/importService.ts` → `src/utils/courseParser.ts`

```
选文件 → parseTimetableWorkbook(字节, 模板锚点)     ← 纯解析：合并单元格展开、周次"5-17周单周"解析
      → importTimetableForStudent(解析结果)          ← 一个数据库事务：
          ① 按学号查助理：有→更新姓名/身份（保留电话QQ）；无→新建
          ② replaceForAssistant：整体替换该生全部课程（重复导入=幂等）
          ③ deriveImportStatus：推导课表状态（空课表=确认无课；有无法识别节次=待核对）
          ④ 写操作日志 ⑤ dataRevision+1
      → findDutyConflicts / findDutyNeedsReview      ← 影响分析：新课程与已写入排班的冲突/待核对清单
```

**为什么要一个事务包住①~⑤**：中途失败（如课程写入出错）会留下"建了助理却没有课表"的半成品。Dexie 事务里任何一步抛错，全部回滚——这在测试里用"故意让某一步抛异常"验证过（故障注入）。

**解析器要点**（courseParser.ts，22 个测试）：学院课表是合并单元格的网格，先定位表头行（锚点"节次/星期"，可被导入模板配置），再把合并区域按左上角值展开，逐格拆"（本）课程号-课程名[班次] + 周次"。识别不了的节次**不丢弃**——标记为问题，导入后该生状态变"待核对"。

### 5.2 自动排班：贪心算法（`src/algorithms/greedy.ts`）

一次生成 17 周（`scheduleAll`），每周独立跑 `scheduleOneWeek`，五个阶段：

```
① 建时段表     工作日 × 上班节次 → 每节一格（key=c{节号}）
② 算课程占用   每人的课换算到"节次序号轴"（见 6.2），有课的格标忙
③ keep 预占    锁定项先入座——但必须先过安全校验（有课/超容量/超个人上限 → 拒绝+原因）
④ 主分配       时段按"候选人数少的先排"（先难后易）；时段内候选按策略排序（见 5.2.1）
⑤ 收尾         修复⇄撤销迭代（低于下限的补位；孤立短段撤销后再补，最多 4 轮）
               → 每日均衡（消除"某天无人"：新建块/搬移整块，只动纯自动块）
               → 终态清理（P08 教训：最后再撤销一次孤立短段，宁缺勿违规）
```

**5.2.1 候选策略**（types.ts `candidateStrategy`，配置页可选）——只改排序维度先后，不碰任何约束检查：

| 策略 | 排序 |
|---|---|
| default | 延续已有连续块 → 已排节数少 → 空闲稀缺 → id |
| scarceFree 稀缺空闲优先 | 空闲少的人先拿安排 |
| identityFirst 身份优先 | 本科生先于研究生 |
| roundRobin 轮换优先 | 已排最少者优先（严格轮流） |

### 5.3 手动调整与撤销（`src/db/manualAdjustService.ts`）

点排班表格子 → `ManualAdjustDialog`。每次操作（增/删/移/锁定/例外登记）：

```
1. 收集整周当前数据 → toEvaluation() 转成评价器输入
2. 心算"改完后的整周" → evaluateSchedule() 独立复算
3. diffViolations(改前, 改后)——只有【新增】的硬违规才拒绝（改前就有的旧问题不背锅）
4. 拒绝时给出人话原因："星期1 c1 该生有课：「操作系统」（第一节-第二节）"
5. 通过 → 写入 + 撤销日志（同一事务） + dataRevision+1
```

**撤销为什么是日志不是快照**：每个操作记录"逆操作所需信息"（新增记整行；移动记来回两个位置）。撤销 = 在新事务里执行逆操作**并再过一次第 3 步校验**——如果这期间课程变了、撤销回去会撞新课，这次撤销被拒绝。快照式 undo 做不到这个。

**CAS（乐观锁）**：所有写操作带 `expectedRevision`（界面上次看到的版本号）。事务里先比对 `config.dataRevision`，不一致 → `StaleDataError`"数据已被其他窗口修改"。两个浏览器窗口同时改同一格，后保存的那个会被拦下——测试里用两条真实数据库连接验证过恰好一个成功。

### 5.4 增量重排（`src/algorithms/incremental.ts`）

对比全量重排（推倒重来），增量以**已写入方案为基准**：

- 输入没变（`dataRevision == scheduleWriteRevision`，可验证）且基准合法 → **零改动**：原样返回，连算都不算；
- 输入变了 → 把基准行**全部**作为 keep 传给贪心（锁定的来源记 manual，自动的仍记 auto）；违法的（新课程撞上）被第③步预占校验拒绝并带原因 → 只有被迫的地方变化；
- 范围外周直接原样输出；
- 差异按（周，星期，时段，人）输出 保留/新增/移除/替换 + 原因——原因来自拒绝明细等**可验证信息**，不编造因果。

### 5.5 导出与隐私（`src/utils/scheduleExport.ts`）

单周/多周（每周一个 sheet）/快照（用快照里固化的姓名与规则）三种导出。三条隐私红线由测试逐单元格扫描保证：

1. 永不写学号/QQ（导出输入根本没有这两个字段——结构上不可能泄）；
2. 电话开关关闭后，**所有** sheet 零电话（不只是主表）；
3. 全部单元格是文本类型——即使有人姓名叫 `=SUM(A1)` 也不会变成公式。

### 5.6 备份与恢复（`src/db/backupService.ts`）

```
备份 = 跨表只读事务拿一致快照 → 序列化成一个 JSON（含内容摘要，只用于检错）
恢复 = 五道校验（JSON？版本不高于本程序？摘要对得上？学号/排班键唯一？引用的人都存在？）
     → 界面确认数量 → 当前数据先存 recovery_backup 独立表 → 单事务整体替换 → 重数一遍记录数
```

换机 = 新机器装应用 → 数据管理页导入这个 JSON。失败（比如文件被改坏）原数据分毫不动。

## 6. 三个值得学会的设计思想

### 6.1 独立评价器：不信求解器的自述

`src/algorithms/evaluate.ts` 是全项目最重要的一块。生成、手调、撤销、恢复、增量——**每个会产出/修改排班的路径，最后都由它复算一遍**：硬违规（课程冲突/超容量/连续段破坏…）存在则不许落库；软缺口（人数不足/低于下限）如实报告但不掩盖。

为什么？项目历史上有个真实教训（审计 P08）：算法的"修复轮"会把孤立的 1 节值班塞回去凑数，而当时的测试只检查第 1 周——缺陷藏在第 3/10/11/12 周。评价器写完当天就把它抓了出来。**教训：任何"生产者自己说合法"的系统都需要一个独立的终审。**

### 6.2 节次序号轴：领域错配的根治（`src/utils/sectionOrder.ts`）

学院课表的节次不是纯数字：`1,2,3,4,5,中课1,中课2,6,7,8,9,10,晚课,11,12,13`。旧版把排班表下午编成 8~11，与课表的 6~9 错位——同一节课两边编号不同，算法漏判，**把人排进了上课时间**。修复：建立唯一"序号轴"（中课1=第6个…），课程区间与排班时段都在这个轴上比较；且连续段不跨午休（上午最后一节与下午第一节不算连续）。

**教训：两个子系统交换"同一概念"时，先统一坐标系。**

### 6.3 版本号 CAS：无锁的并发安全

没有服务器，怎么防两个窗口互相覆盖？借数据库乐观锁的思想：`config` 表存一个只增不减的 `dataRevision`；每个写事务开头校验"我看到的版本还是当前版本吗"，结尾版本+1。同版本的两个写入，后到的在事务里发现版本已变，拒绝并提示刷新。**不需要锁，因为冲突在提交时才被检测。**

## 7. 逐文件导读（改代码从哪下手）

### algorithms/（纯函数，改这里不用碰任何界面）

### workers/ 三个文件

`scheduleJob.ts` 是纯计算内核（生成→改良→评价三阶段，发进度回调）；`scheduleWorker.ts` 是薄壳（收 run 消息、回 progress/result，**不 import 任何 db**）；`scheduleClient.ts` 管生命周期：jobId 递增 + 闭包 done 标志双重防迟到消息、取消=terminate、超时自动取消、环境不支持时回退主线程同一内核。

### utils/ 四个工具

`courseParser.ts`（解析，被模板参数化：三个锚点可配）；`weekParser.ts`（"1-4周,5-17周单周"→区间数组）；`sectionOrder.ts`（序号轴，见 6.2）；`scheduleExport.ts`（见 5.5，版式受导出模板控制：标题{week}占位/列宽/简洁打印）。

### views/ 七个页面

仪表盘（可行动信息：缺课表/缺口/违规，点击直达）、助理管理（四分类状态列+确认按钮）、课程表管理（批量导入+手动编辑+冲突面板）、排班配置（全部规则+策略下拉）、排班表（预览/写入/增量/手调/撤销/快照/导出，项目最重组件）、模板管理、数据管理。

## 10. 常见问题

- **为什么排不满 40 个时段？** 3 人×上限 6 节=18 人节 < 40——缺口如实报告（未满足清单），绝不超上限硬填。
- **为什么有人不参与排班？** 课表状态是"未导入"或"待核对"（助理管理页看得到、可确认）。
- **手动加的人会被重排冲掉吗？** 手动默认锁定；解锁的才会被视为可重新安排。锁定的位置若撞上新课程，重排时会被**拒绝保留**并给原因——锁定不豁免安全约束。
- **数据在哪？** WebView 用户目录下的 IndexedDB（应用名 crsm）。安装到 D 盘不会搬数据；换机用备份文件。
- **两台电脑会同步吗？** 不会——离线应用，备份导入后就是两个独立副本。
