# 排错手册（troubleshooting）

> 按步骤书 0.3 节，项目中有价值的坑位记录于此。格式：现象 → 根因 → 解决 → 教训。

---

## T-001 字体安装后 VS Code 不生效

- **现象**：按 JetBrains Mono 扩展的字体包设置 `editor.fontFamily`，编辑器字体不变。
- **根因**：用命令行注册用户字体时路径拼接少了一个反斜杠（`...\Windows\FontsJetBrainsMono-Regular.ttf`），字体从未真正注册，VS Code 静默回退到备选字体 Consolas，无任何报错。
- **解决**：清理错误注册表项（`HKCU\...\Fonts` 下 `JetBrains Mono *`），用 PowerShell 脚本以 `Join-Path` 拼路径重新复制+注册，并调用 `AddFontResource` + 广播 `WM_FONTCHANGE`；随后**完全退出** VS Code 再启动（Electron 进程只在启动时枚举字体，Reload Window 不够）。
- **教训**：① 字体"静默回退"不报错，排查必须查 GDI 注册结果而不是只看配置；② 跨 shell 拼 Windows 路径时用脚本文件而不是内联命令，避免多层转义；③ 用户字体注册在 `HKCU`，系统级在 `HKLM`，前者无需管理员。

## T-002 Rust 侧重命名需要三处同步

- **现象**：把脚手架 `scaffold-tmp` 改名为 `crsm` 时，若只改 `Cargo.toml` 的 package name，`main.rs` 里的 `scaffold_tmp_lib::run()` 编译报"找不到 crate"。
- **根因**：Tauri 项目 `Cargo.toml` 中 `[lib] name`（如 `crsm_lib`）与 `main.rs` 的调用点、`tauri.conf.json` 的 productName/identifier 是三组独立标识。
- **解决**：package/lib name、lib 调用、productName（安装包名）、identifier（应用唯一 ID）、窗口标题全部同步改。
- **教训**：Rust 编译器会拦住不一致，所以这类问题必现必报——比前端"静默 undefined"友好；改名后先 `cargo check` 再继续。

## T-003 Vue 模板模板编译错误的定位方式

- **现象**：`npm run build` 失败在 `vue-tsc` 阶段，报错行号指向编译产物。
- **解决**：先单独跑 `npx vue-tsc --noEmit` 拿到 .vue 源文件级别的报错行号，再修；不要直接读 vite 打包日志。
- **教训**：前端构建链分"类型检查（vue-tsc）→ 转译打包（vite）"两层，分别排查。

## T-004 Dexie `delete()` 后实例不会自动重开

- **现象**：单测 `beforeEach` 中 `await db.delete()` 后，首个数据库操作抛 `DatabaseClosedError: Database has been closed`，全部用例连挂。
- **根因**：原以为 Dexie 实例在 delete 后的下次操作会自动重开（autoOpen），实测（fake-indexeddb 环境，探针验证）delete 后实例保持 closed，autoOpen 不触发。
- **解决**：`await db.delete()` 之后显式 `await db.open()`。
- **教训**：对库的行为假设要用最小探针验证（10 行代码），而不是凭印象写 12 个用例再全挂；探针法把 30 分钟排查压缩成 1 次 15ms 的运行。

## T-005 管道吞掉命令退出码，带病提交

- **现象**：`npm run build | tail -3 && git commit` 在构建失败（TS6196 未使用类型）时依然执行了提交。
- **根因**：bash 管道的退出码默认取最后一个命令（tail 总是成功），`&&` 判断失真。
- **解决**：验证类命令要么单独跑，要么 `set -o pipefail`；提交前以"重新单独运行验证"为准。
- **教训**：自动化脚本里，`命令 | 美化输出 && 后续动作` 是经典陷阱；验证与提交必须解耦。

## T-006 弹窗表单残留上次数据（watch prop 失效）

- **现象**：GUI 走查发现，连续两次打开"新增助理"弹窗，第二次的表单里残留上一次填写（或编辑）的手机号、班级。
- **根因**：表单初始化写在 `watch(() => props.assistant)` 里。连续新增时该 prop 一直是 `null`，引用未变 → watch 不触发 → 表单不复位。
- **解决**：改为 `watch(visible)`（监听弹窗打开动作）在打开瞬间按 `props.assistant` 重置表单，并 `clearValidate()` 清除上次校验痕迹。
- **教训**：`watch` 依赖的是"值的变化"，`null → null` 不算变化；"打开容器"这类事件语义的状态（布尔量）才是正确的触发源。父组件必须保证先改 `assistant` 再改 `visible`。

## T-007 GUI 自动化中的"僵尸页面"：HMR 与浏览器缓存的混合劣化

- **现象**：开发服务器多次 HMR 后，浏览器内自动化（IAB）出现大面积诡异：Playwright 点击全部 actionability 超时、CUA 键盘事件（Enter/Ctrl+F5）不到达、截图失败、按钮原生 .click() 后 Vue 处理函数不执行、页面运行的模块版本落后于服务端。
- **根因**：长时间会话中 HMR 多次热替换 + guest 页面缓存，导致"服务端代码 / 页面运行代码 / 输入事件通道"三方不一致。表现为任何单一角度的排查都自相矛盾（编辑按钮好用、删除按钮不好用）。
- **解决**：完全重启 Vite（注意 git-bash 的 kill 杀不掉 Windows 进程，要用 `taskkill //F //PID`）→ 浏览器新开标签页 → 加临时 console.log 探针确认运行的代码版本 → 全绿。
- **教训**：① 排查"灵异问题"前先确认三方版本一致（服务器/页面/事件通道）；② `console.log` 探针是判定"代码版本"的最快手段；③ git-bash 下杀 Windows 进程用 taskkill；④ 将 ElMessageBox（命令式服务）替换为声明式 el-dialog 后，确认框行为一致且在该环境下可测——命令式服务在自动化环境中更脆弱。

## T-008 响应式 Proxy 对象写入 IndexedDB 抛 DataCloneError

- **现象**：导入课程确认入库时报 `Failed to execute 'add' on 'IDBObjectStore': [object Array] could not be cloned`。
- **根因**：解析结果存入 Vue `ref` 后变成响应式 Proxy（深层），IndexedDB 的 structuredClone 不能克隆 Proxy 对象。spread 展开（`{...c}`）只是浅拷贝，嵌套的 `weekRanges` 仍是 Proxy。
- **解决**：在数据落库边界**逐字段构造纯对象**（含把嵌套数组显式重建），或用 Vue 的 `toRaw()` 后深拷贝。
- **教训**：① "Vue 状态 ≠ 纯数据"——跨出响应式系统的边界（IndexedDB、fetch body、Web Worker postMessage）必须先脱壳；② 这类错误只在运行时暴露，把落库操作放在仓储层并配集成测试才能尽早拦截。


## T-009 两套节次编号不一致导致"在上课时间排班"

- **现象**：排班结果把助理排在了他有课的时间段里。用户从界面上发现"导入的课程表和排班表的节次显示不一致"：课程表里下午刚开始的两节课是"第6节、第7节"，而排班表把它们标为"第8节、第9节"。
- **根因**：**同一节真实课程在两处编号不同**。实测课程表 A 列时段块得到全天的节次序列是"数字节次 + 命名节次"混排：上午 1~5、中课1/中课2、下午 6~10、晚课、晚上 11~13；而排班表的上班节次默认写成"上午 1~4、下午 8~11"。占用判定原本直接比较**节号区间**，于是课程"第六节-第八节"（真实占下午前三节）只会与排班"第8节"相交，排班"第9、10节"被判定为空闲 → 在这些节次上排班，正好落在课前两节里。更隐蔽的是：因为偏移是 2 而不是"整体错位"，判定结果是"部分相交"，既不会报错也不易被察觉，只会表现为局部错排。
- **解决**：① 排班表上班节次编号改为与课程表一致（上午 1~4、下午 6~9）；② 占用判定不再比较节号，而是**先统一换算到"当日先后序号"**再比较，序号轴集中定义在 `src/utils/sectionOrder.ts`（`SECTION_SEQUENCE`），解析器与算法共用同一换算；③ 迁移存量：`normalizeRules` 把旧默认 [1-4]+[8-11] 对齐为 [1-4]+[6-9]（只迁移与旧默认完全一致的区间），数据库升到 version 3 把 `duty_schedule.timeSlot` 的 c8~c11 就地平移为 c6~c9；④ 回归夹具用三份真实课程表重建，补齐节次原文。
- **教训**：① **同一实体在两处被各自编码，就必须建立显式的换算层**——只要比较的是"编号"而不是"含义"，错配就只是时间问题；② 偏移型错配比整体错位更危险，因为它产生"部分正确"的结果，测试若只覆盖粗粒度场景（如"有课就不排"）很容易漏过；③ "非数字标签一律保守按整天占用"这类兜底虽然安全，但会掩盖真实结构——先花时间把数据摸清（本次靠 A 列时段块 7 个标签就把序列还原出来了），再决定是精确计算还是保守退化；④ 遇到"用户说 A 表和 B 表对不上"的反馈，先做**同一份数据在两处的对照样例**，比读代码猜更快。


## T-010 版本升级里"平移索引键"引发 ConstraintError，整库不可用

- **现象**：导入课程表时报 `Error modifying one or more objects. Errors: ConstraintError: Unable to add key to index '[weekNo+dayOfWeek+timeSlot+assistantId]': at least one key does not satisfy the uniqueness requirements.` 报错发生在"导入"动作上，看起来像导入逻辑的 bug。
- **根因**：**报错根本不在导入路径上**。`Error modifying one or more objects` 是 Dexie 升级事务里 `Collection.modify()` 的固定措辞，而那个索引属于 `duty_schedule` 表。真实链路是：页面首次访问数据库 → Dexie 执行 v3 升级（把下午节次键从 8~11 平移为 6~9）→ 库中同时存在旧标签行与新标签行（先前的中间版本已按新编号写过排班）→ `c8→c6` 撞上已有的 `c6` 行 → 复合唯一索引报错 → **整个升级事务回滚，数据库版本不提升且保持不可用**，于是任何写操作（第一个动作恰好是导入）都失败。导入本身完全无辜。
  更深一层：这个"平移"从语义上就不成立——**同一个键在两套编号下含义不同**（`c8` 旧=下午第一节、新=下午第三节），逐行平移即使不撞键也会把下午节次静默改错。
- **解决**：① 先修"何时升级"——不要在界面已按新编号写入数据之后才补迁移；编号相关的改动要把**默认值、算法、持久化迁移**作为一次原子变更一起发布。② 迁移本身改为**不猜测**：把旧排班归档进 `schedule_snapshot`（留痕）并记一条 `schedule.migrate` 日志，然后清空 `duty_schedule`，由"生成排班"按 (课程表, 规则) 重算——排班是纯函数结果，可完整重建，与 v2 时段键格式变更时的清空策略一致。③ 补 `src/db/migration.test.ts`：用一个"只声明到 version 2"的 Dexie 实例伪造旧库（含**旧新标签并存**的混合态）再触发真实升级，锁定"不抛错 + 归档 + 清空 + 其他表保留"。
- **教训**：① **唯一索引 + 键重映射 = 事务级炸弹**：单行合法、批量非法，失败点还不在调用方以为的地方；凡是升级里要改带唯一约束的键，必须先按"最终键"整体规划并去重，而不是就地逐行改。② **键当且仅当语义稳定时才可以重用**：同一编号在不同版本下换了含义，就应视为新键，旧的必须显式迁移或废弃。③ 用户报"某个按钮出错"时，先看错误措辞属于哪一层（这里是 Dexie 升级事务，而非业务代码），再决定排查方向——否则会在导入逻辑里白找很久。④ 伪造旧版本库来测试迁移，比在真实库上试错安全得多。


## T-011 删除实体只清理了"直接附属"，漏了"派生引用"

- **现象**：删除一名助理后，排班表与导出文件里出现 `#7` 这样的条目（本应是姓名）。
- **根因**：`assistantRepo.remove` 的事务里只级联删除了 `course`（直接附属数据），漏掉了 `duty_schedule`（**引用**该助理的派生数据）。IndexedDB 没有外键约束，引用完整性完全靠应用层自觉。
- **解决**：事务扩到三张表，按 `assistantId` 一并删除排班记录；并用"删除后他人排班保留、本人排班清零"的用例锁死。
- **教训**：① 删除一个实体前，先列出**所有**含其外键的表，逐一对账——无外键约束的存储（IndexedDB/localStorage/文档库）尤其如此；② "级联删除"应该是一个完整清单而不是"想到哪写到哪"。

## T-012 派生视图按"当前配置"渲染，会和历史数据脱节

- **现象**：已写入排班（上午 1~2 节）后，把上班节次改成"下午 6~9 节"，再看排班表/导出文件——数据还在库里，但表格里**所有格子都是 —**，像是被清空了。
- **根因**：网格/导出的行与列完全由**当前规则**推导，而数据行存的是**写入当时**的节次键。配置一变，视图与数据的坐标系就不再对齐。用户改配置后直接导出，交出去的是一张空表。
- **解决**：行列骨架改为「当前规则 ∪ 已写入数据」的**并集**（`src/utils/scheduleGrid.ts`）——规则内的节次照常带时间标注，数据里多出来的节次也会显示（只显示节号/无时间标注的写法），任何已写入数据都可见；排班表页面与导出模块共用同一推导，避免两处口径再漂移。
- **教训**：① 凡是"视图按配置推导、数据按历史快照存储"的组合，都要问一句：配置变了之后，旧数据还能不能被看见？② 用并集而不是"以配置为准"或"以数据为准"，是因为两者各有正确的场景（空表需要配置行、旧数据需要数据行）；③ 该修复顺带消除了"网格列顺序依赖对象整型键升序"的脆弱写法（改为显式传入天数组、按键取值）。


## T-013 xlsx 脱敏：跨文本 run 的敏感串替换会漏改，且整串检测查不出来

- **现象**：对课程表做个人信息脱敏时，按"文本片段"做子串替换后，残留检测显示"无残留"，但打开文件发现**学号仍在**（如 `学生：示例学生A(10240052` 后面还跟着 `54)`）。
- **根因**：OOXML 中同一单元格的文本可以按字体/字符集被 Excel **拆成多个 `<t>` run**。实测三份课表中，两份的表头被拆成三段：
  `学生：李四(10240052` + `54` + `)　　`——目标串 `1024005254` 在任何单个 run 中都不完整存在，因此**替换命中不了**；而残留检测若按原始字节查找整串，同样查不到，形成**假阴性**。第三份文件恰为单 run，顺利替换，反而掩盖了问题。
- **解决**：改为**按单元格（`<si>`）处理**——拼接该单元格全部 run 文本 → 做整体替换 → **按原 run 长度重新切分回填**（run 数与各 run 的 `<rPr>` 样式得以保留，仅文本位移）。残留检测同步改为基于"拼接后的单元格文本"，并补充"10 位学号式数字"扫描，防止同类漏网。
- **教训**：① 凡对 OOXML 文本做查找替换，**必须以单元格为单位**，不要把解析粒度等同于文本 run；② **负向断言（"文件里不该有 X"）在替换前就要设计好检测方法**，否则"替换失败 + 检测漏报"会同时发生，让人以为已经干净；③ 样本里只要有一份文件"侥幸通过"，就必须对**全部样本**逐一验证，而不是抽样；④ 脱敏必须覆盖三层——表头姓名学号、`上课教师` 字段、**以及 `docProps/core.xml` 的 `cp:lastModifiedBy` 元数据**（元数据里存着制作人真名，是最容易漏的一层）；⑤ 结构完整性可用"仅 `sharedStrings.xml` 与 `core.xml` 变化、其余部件字节级一致、合并单元格数量不变"作为判据。


## T-014 批量替换版本号误伤 `Cargo.lock` 中的同名第三方依赖

- **现象**：执行"把项目版本从 1.0.0 改为 0.1.0"的批量文本替换后，`git diff` 显示 `src-tauri/Cargo.lock` **有两处**改动，而本项目的包只有一个。
- **根因**：`Cargo.lock` 是**所有依赖的版本清单**，其中 `defmt-parser` 恰好也发布过 1.0.0，被无差别替换成 0.1.0。锁文件一旦被改坏，`cargo` 会认为锁定版本与 registry 不符，轻则报错、重则静默重写锁文件造成依赖漂移。
- **解决**：替换锚点必须是**包名 + 版本**的组合（`name = "crsm"\nversion = "1.0.0"`）而非孤立的版本字符串；替换后立即用 `git diff` 核对改变行数（本次应为 1 行），并用 `cargo metadata --no-deps --offline` 验证锁文件仍可解析。其他文件同理：`package.json` 的 `version` 字段唯一，但 `package-lock.json` 同样包含大量依赖版本（如 `"@types/estree": "^1.0.0"`），需按缩进/上下文精确匹配。
- **教训**：① **锁定文件与清单文件里的"版本"不是同一个概念**——前者是依赖矩阵，后者是自身版本，批量替换前必须先分清；② 任何批量替换都要**先看命中了多少处**，命中数超出预期就停下来核对，而不是直接写回；③ 版本号这类"元信息"改动最好用脚本 + 断言（期望命中次数），把"改对了几处"变成可验证的检查项；④ 项目版本号需同步的位置固定为六处：`package.json`、`package-lock.json`（两处 `version` 字段）、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock`（crsm 条目）、`src-tauri/tauri.conf.json`、`src/meta.ts`（界面展示 `v0.1`），外加 `README.md` 与 `CHANGELOG.md` 的文档描述。
