# 学院行政办助理排班系统（CRSM）任务指导步骤书

> 本文档是项目的**总教学大纲与执行契约**。它同时服务两个目的：
> 1. 帮助软件工程初学者理解"一个真实项目如何从零到交付"；
> 2. 约束 AI 助手（code-generator）按此路径逐步协作，每一步可验证、可暂停、可回退。
>
> 关联文档：`docs/SRS.md`（做什么）、`docs/ADR-001.md` / `docs/ADR-002.md`（怎么做）、`README.md`。

---

## 〇、教学契约（双方约定）

### 0.1 教学理念：为什么 → 怎么做 → 做出来

每个模块固定三段式：

1. **为什么（Why）**：先讲清楚这个模块解决什么问题、为什么需要它、背后对应软件工程里的哪个概念（如需求分析、数据建模、耦合内聚、算法复杂度、状态管理）。不讲原理不动手。
2. **怎么做（How）**：给出设计方案（2~3 个候选时做对比，遵循 `.zcode/agents/code-generator.md` 工作流），讲清楚技术选型的理由和整体思路。
3. **做出来（Do）**：动手写代码。代码附带结构说明，不留"魔法代码"——每一行都解释过。

> **补充契约（用户要求，不可省略）**：
> 1. **每次生成代码后必须附详细解释**——逐文件/逐关键行讲清楚，包括脚手架生成的代码也不能免讲；
> 2. **听众画像固定**：学习者有后端基础（懂 HTTP、数据库、进程等概念）但**零前端经验**——所有前端概念（组件、响应式、路由、打包、事件循环等）必须首次出现时给出定义 + 与后端世界类比（如：`package.json` ≈ `pom.xml`，Vite ≈ 内嵌的开发服务器+打包器，组件 ≈ 可复用的"视图类"）。

### 0.2 暂停确认点（2026-09-11 修订：自主执行版）

> **契约变更（用户授权）**：用户无法逐项审查内容，改为**模块内自主决策**模式：
> 1. 模块内的设计方案、技术细节由 Agent 自行决定，理由写入模块报告；
> 2. 每模块由 Agent **自检自测**（单元测试 + 构建 + 浏览器 GUI 自动走查）全部通过才算完成；
> 3. **仅在模块边界暂停**：报告含成果清单 / 自测结果 / 关键决策与理由 / 代码详细讲解，用户回复"继续"才进入下一模块；
> 4. 用户可随时要求任意模块返工。

### 0.3 错误处理与排查流程（贯穿全程的标准动作）

遇到报错时按以下流程执行，不许跳步：

1. **完整读取报错**（不猜测、不截断），区分：编译错误 / 运行时错误 / 逻辑错误；
2. **定位**：报错指向哪个文件哪一行？是环境问题、依赖问题还是代码问题？
3. **最小化复现**：用最小的改动确认根因；
4. **修复并解释**：说明"为什么错"而不只是"怎么改"；
5. **记录**：有价值的坑写入 `docs/troubleshooting.md`（累积成项目的踩坑手册）；
6. **回归验证**：修复后必须重跑该模块的验证步骤，确认没引入新问题。

### 0.4 工程习惯（每个模块都要练）

- **Git**：每个模块在独立分支开发（`feat/m01-scaffold`、`feat/m02-db`…），完成后合并回 `main`，提交信息用约定式格式（`feat:` / `fix:` / `docs:` / `test:`）。
- **验证先行**：每个模块定义"完成标准"，不达标不算完成。
- **文档同步**：涉及架构/需求变更时，同步更新 SRS 或新增 ADR。

## 二、各模块详述

### 阶段 0：环境与工程脚手架 📦

**目标**：项目能在开发模式下跑起来，理解"一个 Tauri 项目由哪些部分组成"。

**为什么**：
- 软件工程的第一课：**可运行的骨架先于一切功能**。让"改代码→看效果"的反馈循环先转起来，后面每一步才有即时验证的土壤。
- 认识现代前端的工程结构：包管理（npm）、构建工具（Vite）、类型系统（TypeScript）、组件框架（Vue 3）各自的角色。

**怎么做**：
- 用官方脚手架 `create-tauri-app`（vue-ts 模板）生成，合入现有仓库（保留 docs/README/.gitignore）。
- 补装运行时依赖：`dexie`（数据库）、`vue-router`（页面路由）、`pinia`（状态管理）、`element-plus`（UI 组件库）。
- 讲解目录结构：`src/`（前端源码）、`src-tauri/`（Rust 壳）、`vite.config.ts`（构建配置）。

**验证方式**：
- `npm run dev` → 浏览器出现欢迎页；
- `npm run build` → 构建通过（Rust 编译留到阶段 7，避免初学阶段等待过长）。

**常见错误排查**：npm 源网络问题（换镜像）、Node 版本不匹配（`node -v` 检查 ≥18）、端口占用。

**暂停确认点**：欢迎页可见 + 目录结构讲解完毕。

---

### 阶段 1：数据层（Dexie）🗄️

**目标**：按 ADR-002 第 5.2 节的定义，建立 6 张表及类型安全的 CRUD 封装。

**为什么**：
- **数据建模是软件设计的核心**：表结构定错，后面全部返工（我们在 ADR 阶段已经踩过一次"漏周次字段"的坑）。
- 理解 IndexedDB 与关系型数据库的异同：索引、主键、无 SQL；理解为什么用 Dexie 封装（Promise 化、版本化 schema 迁移）。
- 软件工程概念：**数据字典、模式（Schema）、迁移（Migration）、关注点分离**（数据层不掺 UI 逻辑）。

**怎么做**：
- `src/db/schema.ts`：用 TypeScript 接口定义每张表的字段（与 ADR-002 5.2 一一对应）；
- `src/db/database.ts`：Dexie 实例 + `version(1).stores(...)` 声明索引；
- `src/db/repositories.ts`：每张表一个仓储对象（`assistantRepo.add/update/remove/list`…），UI 永远不直接碰 Dexie。

**验证方式**：
- 安装 `fake-indexeddb`，用 Vitest 写仓储层单元测试（增删改查、唯一约束如学号重复）；
- 手动验证：浏览器 DevTools → Application → IndexedDB 能看到表。

**常见错误排查**：schema 改了但浏览器里还是旧表（版本号没升）、`undefined` 主键报错、TypeScript 类型不匹配。

**暂停确认点**：单测全绿 + DevTools 截图。

---

### 阶段 2：助理信息管理（F02）👤

**目标**：第一个完整的增删改查页面——表单、列表、校验、交互反馈。

**为什么**：
- CRUD 是管理系统的原子能力，先在"最简单的数据"上把套路练熟，后面课程表、排班页全是它的变体。
- 软件工程概念：**表单校验（前端防线）、组件化（表单组件与列表组件的职责拆分）、用户反馈（成功/失败提示）**。

**怎么做**：
- 路由搭建（`vue-router`）：仪表盘/助理管理/课程表/排班配置/排班表五个空页面，先通骨架；
- `AssistantList.vue`（表格 + 搜索）与 `AssistantForm.vue`（弹窗表单）拆分；
- Element Plus 表单校验规则：姓名非空、学号唯一、手机号正则、身份类型枚举。

**验证方式**：手动走查——新增（含非法输入被拦截）、编辑、删除（带确认框）、搜索过滤。

**常见错误排查**：表单校验不触发（`rules` 未绑定）、弹窗关闭后数据未刷新（响应式丢失）、el-form ref 为空。

**暂停确认点**：完整走查一遍 CRUD 流程。

---

### 阶段 3：课程表导入（F05 导入侧 / F06）📥

**目标**：解析 `timeTableForStu12.xlsx` 样例，批量入库，行级错误提示。

**为什么**：
- 这是全项目**唯一不能纸上谈兵的模块**：真实世界的数据是脏的（65 个合并单元格、多行文本、"上课时间暂未确定"自由区）。软件工程概念：**防御性编程、数据清洗、错误边界**。
- 先读 SRS 附录 A（我们实测过的格式定义），理解"解析器是把非结构化文本翻译成结构化数据的翻译官"。

**怎么做**：
- SheetJS 读文件 → 定位表头区/网格区 → 处理合并单元格 → 逐单元格解析"（身份）课程号-课程名[班次]"与周次文本；
- 周次解析器单独写纯函数（`"1-4周"` `“10周”` `“6-17周单周”` → 数组），因为它最容易出错、最值得单测；
- 解析结果先展示预览（导入多少条、哪些行失败），用户确认后才写库。

**验证方式**：
- 周次解析函数单元测试（边界：单周、多段、非法输入）；
- 用真实样例文件导入，核对条数与内容。

**常见错误排查**：合并单元格取值只有左上角有值（其余为空）、中文全角括号/逗号、学期字符串带全角空格。

**暂停确认点**：样例文件导入结果核对无误。

### 阶段 4：排班算法（F01 / F03）⚙️

**目标**：实现 ADR-002 3.4 节约定的贪心启发式排班，5 秒内出结果。

**为什么**：
- 项目的灵魂。先学**把业务问题翻译成计算问题**：助理-时段二分图、人数上下限、工时上下限 → 约束满足问题（CSP）。
- 软件工程概念：**纯函数**（同样的输入永远同样的输出、不碰数据库不碰 UI——所以能被彻底测试）、**复杂度意识**（O(n×m) 为什么够快）、**策略模式**（换算法不动业务）。

**怎么做**：
- `src/algorithms/types.ts`：算法输入/输出类型（与数据层解耦）；
- `src/algorithms/greedy.ts`：空闲矩阵计算 → 时段按约束紧度排序 → 候选按空闲度分配 → 工时校验与局部调整；
- `src/algorithms/greedy.test.ts`：构造小型固定用例（3 助理 × 2 时段 × 各种约束）逐一验证。

**验证方式**：
- 单元测试全绿（含无解场景给出明确报告）；
- 用 10 个虚拟助理 × 17 周跑全量，计时确认毫秒级。

**常见错误排查**：时区/星期偏移（day 0-6 vs 1-7 的约定混乱）、约束传递遗漏导致死循环、修改输入对象造成副作用。

**暂停确认点**：测试全绿 + 用样例数据演示一次完整排班。

---

### 阶段 5：排班表 UI 与手动调整（F04）📅

**目标**：周视图排班表格展示 + 拖拽/点选手动调整 + 冲突警告 + 撤销/重做。

**为什么**：
- 数据变成"人能看懂的东西"才算产品。学习**展示与数据分离**（同一份排班数据渲染成周视图/列表视图）。
- 撤销/重做用 ADR-002 定的**快照栈**：为什么在大规模下命令模式更优、而本项目选快照栈（数据量小、F08 差异对比免费获得）——这是典型的**权衡（trade-off）**思维训练。

**怎么做**：
- Pinia store 管理"当前排班数据 + undo 栈 + redo 栈"；
- 周视图：Element Plus 表格自定义渲染，时段 × 星期网格；
- 手动调整入口（指派/移除）→ 实时约束校验 → 违规给警告但允许强制（管理员豁免权，记 operation_log）。

**验证方式**：手动走查——调整后警告出现、撤销/重做往返、刷新页面后数据与快照一致。

**常见错误排查**：快照存了引用而非深拷贝（撤销后数据还是变的）、store 外直接改对象绕过响应式。

**暂停确认点**：完整演示"自动排班 → 手改 → 撤销 → 重做"。

---

### 阶段 6：导出与重新排班（F05 导出侧 / F08）📤

**目标**：排班表导出为格式化 xlsx；重排保留手动项并支持前后 diff。

**为什么**：
- 导出是系统对外的"交付物"，格式好坏直接影响行政办老师是否真的用它。学习**面向输出设计**（先拿一张真实排班表打印件倒推 xlsx 的表头/合并/列宽）。
- 重排差异对比基于阶段 5 的快照 diff——体会前期决策（快照栈）如何降低后期成本。

**怎么做**：
- SheetJS `writeFile` 生成 xlsx：表头合并、冻结首行、列宽、状态列配色；
- 重排：`source === 'manual'` 的记录保留 → 其余重算 → 新旧快照 diff 渲染对比视图（新增/移除/不变三色）。

**验证方式**：导出文件用 Excel 与 WPS 各打开一次核对；重排前后对比视图人工核对若干条。

**常见错误排查**：中文文件名乱码、合并单元格写法与读法不对称、WPS 兼容性差异。

**暂停确认点**：交付一份能直接打印的排班表 xlsx。

### 阶段 7：Tauri 桌面化交付 🖥️

**目标**：集成文件对话框/保存插件，打包出可安装的 `.exe`。

**为什么**：
- 理解 Tauri 架构：前端 WebView + Rust 壳，官方插件（dialog/fs）让我们**零 Rust 代码**拿到系统能力——验证 ADR 阶段的判断。
- 软件工程概念：**打包与发布（release engineering）**、版本号、安装包。

**怎么做**：
- 安装 `@tauri-apps/plugin-dialog`、`@tauri-apps/plugin-fs`，改造导入/导出入口走系统文件对话框；
- `npm run tauri build` 产出安装包（首次 Rust 编译 5~15 分钟，属正常现象）。

**验证方式**：安装包在另一台 Windows 10 机器（或本机）安装运行，导入+排班+导出全流程走通。

**常见错误排查**：Rust 编译缺 MSVC 工具链（装 VS Build Tools）、WebView2 缺失、插件权限未在 `tauri.conf.json` 声明。

**暂停确认点**：拿到可分发的安装包。

### 阶段 8：工程收尾与复盘 🏁

**目标**：测试补全、性能核对、文档定稿、发布 v0.1。

**为什么**：
- 软件工程课程最容易被忽视但最加分的部分：**可维护性与复盘**。回顾 ADR 里的预测哪些准了哪些偏了，是学习效果最好的一环。

**怎么做**：
- 补齐 SRS 4.1 性能指标验证（50 人 5 秒内）、操作日志落地检查；
- README 定稿（截图、快速开始、已知限制）；
- 数据备份/恢复功能（对应风险 R03）收尾；
- 全量测试 + 打 tag `v0.1.0`。

**验证方式**：按 SRS 非功能需求逐条打勾，形成验收清单。

**暂停确认点**：v0.1 发布。

## 三、Agent 执行约定（给我自己的备忘）

1. 每次会话开始，先读本步骤书与对应 ADR，确认当前所处模块，不跳步；
2. 每个模块内部严格遵循 code-generator 工作流：**原理讲解 → 方案对比 → 等待确认 → 编码**；
3. 模块完成即暂停，汇报"成果清单 + 验证结果 + 下一步预告"，等用户确认；
4. 所有报错按 0.3 节流程处理，重要坑位写入 `docs/troubleshooting.md`；
5. 每模块一个 git 分支，完成合并，提交信息规范化；
6. 需求/架构如需变更：先改文档（SRS/ADR），再改代码，保持文档与实现一致。
