## 一、决策背景

本项目为软件工程课程项目——学院行政办助理排班系统。系统面向学院行政办，用于管理学生助理的排班工作。项目约束条件为：

- **无服务器环境**：项目不涉及后端服务器部署
- **单机使用**：由行政办老师在本地电脑使用
- **数据持久化**：数据需在本地持久保存，不因关闭应用而丢失
- **导入导出**：支持课程表导入和排班表导出（Excel格式）

基于以上约束，需要决策两个核心问题：

1. **数据存储方案**：在浏览器本地存储与后端数据库之间如何选择？
2. **应用打包方案**：如何包装为可在电脑上直接打开的应用？

## 二、数据存储方案

### 2.1 方案A：localStorage

**描述**：利用浏览器内置的 `localStorage` API 存储键值对数据。

**优点**：

- 零配置，API 简单（`setItem` / `getItem`）
- 同步读写，开发门槛低
- 无需额外依赖库

**缺点**：

- 容量限制严格（通常 5MB 以下）
- 仅支持字符串存储，复杂数据结构需手动序列化
- 无法建立索引，查询性能随数据量增长急剧下降
- 不适合存储结构化表格数据（如课程表、排班表）

**适用场景**：系统配置、用户偏好等小量简单数据。

### 2.2 方案B：IndexedDB（已采纳）

**描述**：浏览器内置的结构化数据库，支持存储对象、数组等复杂数据结构，支持索引和事务。

**优点**：

- 容量大（无硬性上限，通常数百MB起步）
- 支持结构化数据查询（类似数据库的索引和事务）
- 异步操作，不阻塞主线程
- 数据持久化，关闭应用后数据不丢失
- 可通过封装库（如 Dexie.js）简化 API 调用

**缺点**：

- 原生 API 较复杂（回调地狱），需封装库降低使用门槛
- 不支持 SQL 查询，复杂关联查询需应用层实现
- 数据孤岛，不同设备间不互通

**封装库选择**：

| 库名 | 特点 | 选择理由 |
|------|------|---------|
| **Dexie.js** | 基于 IndexedDB 的 Promise 封装，API 简洁，支持表定义和索引 | 推荐，学习成本低，文档完善 |
| localForage | localStorage 的异步封装，API 极简 | 功能较单一，不适合复杂查询场景 |

**最终选择**：**IndexedDB + Dexie.js**

**数据表设计**（2026-09-10 修订：补充周次、学号、来源标记、操作日志与快照表，修订依据见 ADR-002 第五节）：

| 表名 | 说明 | 核心字段 |
|------|------|---------|
| `assistant` | 助理信息 | id, 姓名, **学号（唯一）**, 电话, QQ, 班级, 身份类型(本科/研究生) |
| `course` | 课程表 | id, assistant_id, 课程编号, 课程名, **上课周次（如 [[1,4],[6,17]]）**, 星期, 节次(起止), 上课地点, 教师 |
| `duty_schedule` | 排班表 | id, **周次**, 星期, 时段, assistant_id, 状态, **来源(auto/manual)** |
| `config` | 系统配置 | key, value（排班规则、人数限制等） |
| `operation_log` | 操作日志 | id, 操作时间, 操作类型, 操作详情（满足 SRS 4.2 追溯要求） |
| `schedule_snapshot` | 排班快照 | id, 创建时间, 标签, 排班数据(JSON)（支撑撤销/重做与重排对比） |

### 2.3 方案C：后端数据库（SQLite / MySQL）

**描述**：搭建后端 API 服务 + 关系型数据库，采用前端→后端→数据库的三层架构。

**优点**：

- 数据持久化且安全，不依赖浏览器
- 支持多端同步和多人协作
- 数据完整性有保障（事务、约束、索引）
- 可扩展性强

**缺点**：

- 需要搭建后端服务（Flask/FastAPI/Express），开发成本高
- 需要服务器环境部署，不符合本项目"无服务器"约束
- 学习曲线陡，需掌握后端框架、数据库 SQL、API 设计等

**最终选择**：**不采用**。本项目为课程简易项目，无服务器环境，不满足多端协作需求，采用此方案过度设计。

### 2.4 数据存储方案对比总结

| 对比维度 | localStorage | IndexedDB（已采纳） | 后端数据库 |
|---------|-------------|-------------------|-----------|
| 开发难度 | 低 | 中 | 中高 |
| 数据容量 | 小（~5MB） | 大（无硬性上限） | 无限制 |
| 数据结构支持 | 仅字符串 | 结构化对象 | 关系型表 |
| 查询能力 | 弱（仅键查找） | 中（索引+事务） | 强（SQL） |
| 多端同步 | 不支持 | 不支持 | 支持 |
| 部署难度 | 零 | 零 | 中高 |
| 适用场景 | 简单配置 | 结构化本地数据 | 生产级应用 |

## 三、应用打包方案

### 3.1 方案A：Electron 打包

**描述**：使用 Electron 框架将 Web 技术（HTML/CSS/JS）打包为桌面应用程序。

**优点**：

- 生态成熟，社区资源丰富，教程多
- 拥有完整的 Node.js 能力，可自由访问本地文件系统
- 打包产物为独立 `.exe`（Windows）/ `.dmg`（Mac），用户体验好
- 支持文件对话框、系统通知等桌面能力

**缺点**：

- 打包体积大（约 80-150MB），因为捆绑了 Chromium 浏览器引擎
- 内存占用较高
- 启动速度相对较慢

**打包产物**：一个 `.exe` 安装包，双击安装后在桌面生成快捷方式。

### 3.2 方案B：Tauri 打包（已采纳）

**描述**：使用 Tauri 框架，前端用 Web 技术编写，后端用 Rust 实现，调用系统自带的 WebView2 渲染页面。

**优点**：

- 打包体积极小（约 3-10MB），不捆绑浏览器引擎
- 内存占用低，性能优秀
- 调用系统自带 WebView2（Windows 10/11 自带），无需额外安装浏览器
- 同样支持本地文件读写，导入导出功能完整
- Rust 后端提供内存安全保证

**缺点**：

- 需要用户系统为 Windows 10 以上（Tauri v2 依赖 WebView2）
- 社区生态相比 Electron 较小，部分插件可能不兼容
- 学习曲线稍陡（需了解 Rust 基础概念）

**打包产物**：一个轻量级 `.exe` 安装包（约 3-10MB），双击即可运行。

**最终选择**：**Tauri**

选择理由：本项目为课程项目，打包体积小更便于分发和提交作业；性能足够满足排班系统的功能需求；Rust 后端的学习本身也是软件工程课程的良好实践。

### 3.3 方案C：直接双击 HTML 文件

**描述**：不打包，直接将 `.html` 文件双击用系统默认浏览器打开使用。

**优点**：

- 零打包，开发调试最直接
- 无需安装任何运行时环境

**缺点**：

- 现代浏览器对 `file://` 协议有严格的安全限制
- `localStorage` 和 `IndexedDB` 在 `file://` 下可能无法正常使用或数据不持久
- 部分浏览器会阻止本地文件读取操作
- 用户体验差（地址栏显示文件路径，无独立窗口）

**最终选择**：**不采用**。体验不稳定，不满足工程交付标准。

### 3.4 应用打包方案对比总结

| 对比维度 | Electron | Tauri（已采纳） | 直接HTML |
|---------|----------|----------------|---------|
| 打包体积 | 大（80-150MB） | 小（3-10MB） | 无 |
| 内存占用 | 高 | 低 | 低 |
| 本地文件访问 | 支持 | 支持 | 受限 |
| 系统要求 | 任意 | Windows 10+ | 任意 |
| 用户体验 | 好（独立窗口） | 好（独立窗口） | 差（浏览器标签页） |
| 开发难度 | 中 | 中偏高 | 低 |
| 适用场景 | 大型桌面应用 | 轻量级桌面应用 | 原型演示 |

## 四、导入导出功能设计

### 4.1 课程表导入流程

```
用户点击"导入课程表"按钮
    → 弹出系统文件选择对话框
    → 用户选择 Excel 文件（.xlsx）
    → 前端使用 xlsx.js 解析文件内容
    → 解析结果映射为内部数据模型（助理ID + 课程名 + 周次 + 时间 + 地点）
    → 调用 Dexie.js 写入 IndexedDB
    → 提示导入成功/失败及详情（行级错误提示）
```

**核心依赖库**：

| 库名 | 用途 |
|------|------|
| **xlsx.js（SheetJS）** | 浏览器端解析/生成 Excel 文件 |
| **Dexie.js** | IndexedDB 封装，数据持久化存储 |

### 4.2 排班表导出流程

```
用户点击"导出排班表"按钮
    → 从 IndexedDB 读取排班数据
    → 使用 xlsx.js 将数据格式化为 Excel 工作表
    → 调用 xlsx.js 的 writeFile 方法触发下载
    → 用户选择保存位置
    → 提示导出成功
```

### 4.3 导入导出文件格式说明

- **导入格式**：仅支持 `.xlsx` 格式课程表文件（学院原始 Word 课程表转换而来，格式定义见 SRS 附录A）；**不支持** `.doc/.docx` 等 Word 格式的直接解析，需先另存/转换为 `.xlsx`（项目附转换指引）
- **导出格式**：生成 `.xlsx` 格式的排班表文件，兼容 Microsoft Excel 和 WPS
- **样例文件**：`timeTableForStu12.xlsx`（项目根目录）为标准输入格式的实际样例，含合并单元格与多行课程单元格，解析器设计以此为基准

## 五、技术栈总览

| 层级 | 技术选型 | 说明 |
|------|---------|------|
| **前端框架** | Vue 3 + TypeScript | 组件化开发，响应式 UI（选型见 ADR-002） |
| **UI 组件库** | Element Plus | 快速构建表单、表格等界面（见 ADR-002） |

| **排班算法** | 贪心启发式 | 自动排班核心（见 ADR-002） |
| **撤销/重做** | 快照栈 | 支撑手动调整与重排对比（见 ADR-002） |
| **应用打包** | Tauri | 轻量级桌面应用打包 |
| **后端运行时** | Rust（Tauri 内置） | 系统级能力调用 |
| **版本管理** | Git + GitHub | 代码托管与协作 |
| **工程文档** | Markdown | ADR、SRS 等文档 |

## 六、风险与缓解措施

| 风险编号 | 风险描述 | 影响等级 | 缓解措施 |
|---------|---------|---------|---------|
| R01 | IndexedDB 在不同运行环境中实现可能存在差异 | 中 | 使用 Dexie.js 统一封装；应用固定运行于 Tauri WebView2（Windows 10+），环境一致性好 |
| R02 | Tauri 要求 Windows 10 以上系统 | 中 | 明确最低系统要求并在 README 中说明；如需兼容旧系统可回退 Electron |
| R03 | 清除应用数据可能导致数据丢失 | 中 | 提供数据导出备份功能，引导用户定期导出备份；在首次使用时提示数据重要性 |
| R04 | xlsx.js 处理大文件时性能下降 | 低 | 设置文件大小上限提示；对超大文件分批处理 |
| R05 | Tauri 生态插件不如 Electron 丰富 | 低 | 核心功能（文件读写、数据库）Tauri 均原生支持；必要时可通过 Rust crate 扩展 |
| R06 | 学生课程表格式不统一导致导入失败 | 高 | 提供标准课程表模板文件供用户填写；导入时做格式校验并给出行级错误提示；Word 格式统一转换为 xlsx 后导入 |

## 七、后续演进路径

### 阶段一：MVP（最小可行产品）

- 纯前端 + IndexedDB 实现核心排班逻辑
- Tauri 打包为桌面应用
- 支持课程表导入、自动排班、手动调整、排班表导出

### 阶段二：功能完善

- 增加排班规则配置（最短/最长上班时间、同时段人数限制等）
- 增加助理信息管理（姓名、电话、QQ、班级等）
- 增加排班冲突检测与提醒
- 可选：将排班算法升级为最小费用最大流以提升解质量

### 阶段三：云端协作（可选）

- 如有需要，可逐步接入后端服务（FastAPI + SQLite/MySQL）
- 实现多端数据同步和多人协作
- 此阶段需重新评估架构，可能引入后端框架

### 演进原则

采用**迭代开发策略**：先做出可运行的原型验证核心逻辑，再逐步增强功能和完善工程规范。这种"先原型后正式"的做法是软件工程中常见的敏捷开发实践。

## 八、决策记录

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 数据存储 | IndexedDB + Dexie.js | 容量大、支持结构化数据、零后端、符合项目约束 |
| 应用打包 | Tauri | 体积小、性能好、适合课程项目分发 |
| 导入导出 | SheetJS (xlsx.js) | 浏览器端 Excel 读写标准库，兼容性好 |
| 后端方案 | 暂不采用 | 项目无服务器环境，过度设计 |
| 前端框架 | Vue 3 + TypeScript + Element Plus | 中文生态友好、组件匹配度高（详见 ADR-002） |
| 排班算法 | 贪心启发式 | 满足性能要求，F04 手动调整兜底（详见 ADR-002） |
| 撤销/重做 | 快照栈 | 实现简单，支撑 F08 差异对比（详见 ADR-002） |
