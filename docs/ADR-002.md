## 一、决策背景

ADR-001 完成了数据存储（IndexedDB + Dexie.js）与应用打包（Tauri）的选型，但遗留以下待定项与缺口：

1. 前端框架在 ADR-001 技术栈表中标记为"Vue 3 / React（待定）"；
2. SRS 的核心功能 F01（自动排班）未约定具体算法；
3. SRS 的 F04（撤销/重做）与 F08（重排差异对比）未约定实现机制；
4. ADR-001 初版数据表缺少 SRS 明确要求的字段（课程周次、学号、排班来源标记），将直接导致空闲时间计算错误与重排功能失效。

本文档对以上问题逐一决策，并同步修订 ADR-001 与 SRS 的对应章节。

## 二、前端框架选型

### 2.1 候选方案对比

| 对比维度 | Vue 3 + TS + Element Plus（已采纳） | React + TS + Ant Design | 原生 JS（无框架） |
|---------|------|------|------|
| 学习曲线 | 模板语法直观，上手快 | JSX 心智负担略高 | 无框架学习成本，但样板代码多 |
| 组件生态 | Element Plus 表格/表单/日期组件齐全，中文文档完善 | Ant Design 组件质量高 | 需手写或拼装零散库 |
| 与本项目匹配度 | 周视图排班表格、CRUD 表单均为其强项 | 匹配度相当 | 6 类页面 + 复杂周视图，手写 DOM 成本高 |
| 团队匹配 | 课程项目主流，中文资料丰富 | 生态最大，但团队无既有经验 | - |

### 2.2 最终选择

**Vue 3 + TypeScript + Element Plus**。

理由：中文资料与组件库对本项目最友好；表格与表单密集型界面正是 Element Plus 的强项；TypeScript 提供类型安全，降低排班数据结构出错的风险。

## 三、排班算法选型（SRS F01）

### 3.1 问题建模

自动排班本质是一个**约束满足问题（CSP）**：将"助理-时段"视为二分图匹配，约束包括同时段人数上下限、每人工时上下限，目标是生成无冲突且覆盖完整的排班方案。

### 3.2 候选方案对比

| 对比维度 | 贪心启发式（已采纳） | 回溯搜索（CSP） | 最小费用最大流 |
|---------|------|------|------|
| 基本思路 | 约束最紧的时段优先分配，候选按剩余空闲时间排序，冲突时局部修复 | 系统性搜索 + 剪枝求可行解 | 工时上下限建模为图论费用 |
| 时间复杂度 | O(n×m)，50人×约百时段毫秒级 | 最坏指数级，依赖剪枝质量 | 多项式级，但实现复杂 |
| 解的质量 | 非全局最优 | 可行性保证强 | 解质量有理论保证 |
| 实现难度 | 低 | 高 | 高 |
| 兜底手段 | F04 手动调整即为设计好的兜底 | - | - |

### 3.3 最终选择

**贪心启发式**。

理由：SRS 4.1 要求 50 人 5 秒内完成排班，贪心算法毫秒级即可满足；解不保证全局最优，但 F04 的手动调整功能本就是流程的一部分，最优性要求可以放宽。升级路径：若后续对解质量有更高要求，可在阶段二引入最小费用最大流替换核心分配器，对外接口不变。

### 3.4 算法流程约定

1. 计算每位助理的空闲时间矩阵（课程表取反，按周次过滤）；
2. 对排班时段按"约束紧度"排序（要求人数多、可用人少的时段优先）；
3. 对每个时段，从候选人中按剩余可用工时/空闲度排序依次分配，直至满足人数要求；
4. 全部分配后校验每人工时上下限，违反者触发局部调整（在可交换的时段间调换）；
5. 输出排班结果及未满足时段清单，交由手动调整处理。

## 四、撤销/重做机制选型（SRS F04、F08）

### 4.1 候选方案对比

| 对比维度 | 快照栈（已采纳） | 命令模式 |
|---------|------|------|
| 基本思路 | 每次改动序列化整份排班数据入栈，撤销=弹栈恢复 | 每个操作记录其逆操作 |
| 实现复杂度 | 低 | 高 |
| 内存开销 | 本项目规模（50人×17周）单份快照约几十 KB，可忽略 | 极小 |
| 对 F08 的支撑 | 重排前后差异对比 = diff 两份快照，几乎零额外成本 | 需额外实现差异计算 |

### 4.2 最终选择

**快照栈**。

理由：数据规模小，快照成本可忽略；实现简单可靠；F08 的"重排前后对比"直接基于快照 diff 实现。快照持久化存储于 IndexedDB 的 `schedule_snapshot` 表，应用重启后仍可恢复历史。

## 五、数据模型修订

### 5.1 缺口与影响

| 缺口 | 影响 | 修订 |
|------|------|------|
| `course` 表缺少上课周次 | 空闲时间计算错误（"1-4周有课"会被当成全学期有课） | 增加结构化字段：`week_ranges`（JSON 数组，如 `[[1,4],[6,17]]`）、`day_of_week`、`section_start/end` |
| `assistant` 表缺少学号 | SRS 5.3 要求学号唯一；导出与 F08 对比依赖学号 | 增加 `student_no`（唯一索引） |
| `duty_schedule` 缺少周次与来源标记 | 无法按周排班；F08"保留手动调整"无从实现 | 增加 `week_no`、`source`（auto/manual） |
| 操作日志无落点 | SRS 4.2 要求修改可追溯 | 新增 `operation_log` 表 |

### 5.2 修订后的数据表定义

| 表名 | 字段 | 说明 |
|------|------|------|
| `assistant` | id (PK), student_no (唯一), name, phone, qq, class, identity (undergrad/graduate), created_at, updated_at | 助理信息 |
| `course` | id (PK), assistant_id (外键→assistant), course_no, course_name, week_ranges (JSON), day_of_week (1-7), section_text, section_start, section_end, location, teacher, note | 课程；week_ranges 决定课程在哪些周生效。2026-09-11 修订：实际样例中节次含非数字标签（中课/晚课），新增 section_text 保留原文，section_start/end 允许 null；实验课批次信息存 note |
| `duty_schedule` | id (PK), week_no, day_of_week, time_slot, assistant_id (外键), status, source (auto/manual), created_at, updated_at | 排班结果；source 标记手动调整项，重排时予以保留 |
| `config` | key (PK), value (JSON) | 排班规则、时段定义、人数限制等 |
| `operation_log` | id (PK), operated_at, action, detail (JSON) | 操作日志，满足 SRS 4.2 追溯要求 |
| `schedule_snapshot` | id (PK), created_at, label, data (JSON) | 排班快照，支撑撤销/重做与 F08 差异对比 |

该定义已同步更新至 ADR-001 第 2.2 节。

## 六、决策记录

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 前端框架 | Vue 3 + TypeScript + Element Plus | 中文生态友好、组件匹配度高、课程项目主流 |
| 排班算法 | 贪心启发式 | 满足性能要求、实现复杂度低，F04 手动调整兜底；阶段二可升级最小费用流 |
| 撤销/重做 | 快照栈 | 实现简单，天然支撑 F08 差异对比 |
| 数据模型 | 补充周次/学号/来源标记/操作日志 | 修复会导致排班错误与功能失效的缺口 |

## 七、修订记录（2026-09-11，新增需求驱动）

1. **排班模式**：新增"各周排班相同"（uniform）模式——以周期内任一周有课即占用，生成一份方案复制到全部周次；默认"各周独立"。算法 API 由单周 `scheduleWeek` 调整为 `scheduleAll`（内部逐周或统一计算）。
2. **课程占用过滤**：Course 表新增 `kind` 字段（theory/experiment，由样例标记（本）/（实）推导），规则可配置两类课程是否计入占用；数据库升级至 version 2 做存量回填。
3. **上班时间表**：时段不再使用固定模板，由规则中的工作日（默认周一~五）× 上班节次（默认上午 1~4 节、下午 6~9 节）推导；`duty_schedule.timeSlot` 存节次区间键（如 `c1-4`），排班表按时段节次显示。
4. **每日均衡**（2026-09-13）：新增规则 `balanceDaily`（默认 true）。贪心主分配按"时段紧度先难后易"逐时段填人，容量会优先消耗在排序靠前的日子上，可能出现"周一~周四已排妥、周五无人"。因此在收敛结果之上追加**每日均衡阶段**，判据是"该工作日的每个上班节次都达到人数下限"（下限取 `max(1, minPerSlot)`，即"某天无人"一律视为不达标）。可用手段分两档：
   - **A 档 · 零损伤**：① 为助理在该天新建满足最少连续节数的连续块；② 把某助理的整个连续块搬到该天的空闲连续段（块节数不变 ⇒ 工时净变化为 0）。均要求**源时段移出后仍满足 `minPerSlot`**（只动用冗余值班），不新增未满足时段。择优选人时以"已值班天数最少者优先"。
   - **B 档 · 兜底让位**（2026-09-13 追加，由实测反馈驱动）：A 档要求"源时段移出后仍满足人数下限"，在**工时上限已用尽**的数据上等价于禁止一切搬移——实测三助理夹具（3 人 × 上限 6 节 = 18 人节 vs 40 个时段，且每个已排时段恰好 1 人、冗余数为 0）下，第 1 周周五永远无人。故追加兜底：仅当某工作日**一个人都没有**且 A 档无解时，允许搬走整个连续块、把源时段的覆盖让出来，从而保证"每天都有人"。硬性闸门：**源日让出后仍须有 ≥1 条排班**（绝不把空白天转移给别的日期）；择优顺序为损伤最小（跌出人数下限的源时段个数）→ 块最短 → 源日值班最多（从最拥挤的天让出）→ 助理 id（确定性）。
   - **取舍（显式记录）**：该夹具下 `18 < 40`，"每个时段都有人"数学上不可达，"每天都有人"与"每时段都有人"不可兼得。实现显式优先前者（需求核心目标），被让出的时段进入未满足时段清单交由手动调整兜底——这是有意的产品取舍，而非静默破坏约束。实测效果：全周期空白天次 **22 → 0**、未满足时段 **399 → 374**（未增加），每人工时与排班总量守恒。
   - *为什么不做"每日人数差最小化"*：各工作日上班节次相同 ⇒ 每日时段数相同，主分配本就会把每个时段填到人数上限，真正的失衡形态就是"某天归零"；而搬移粒度受最少连续节数约束、无法细分到单节微调人数差，强行迭代会在两个状态间来回搬运、永不收敛。故收敛目标锁定为"消除整天无人"。
   - 该阶段不引入新数据结构，也不需要数据库版本升级。

5. **节次序号轴（2026-09-13，缺陷修复）**：实测课程表的节次是"数字节次 + 命名节次"**混排**的连续序列——上午第 1~5 节、午间"中课1/中课2"、下午第 6~10 节、傍晚"晚课"、晚上第 11~13 节（顺序取自课程表 A 列时段块）。原设计把排班表的下午编为第 8~11 节，而课程表编为第 6~9 节，**同一节真实课程在两表中编号相差 2**；占用判定按节号比较区间时会漏判——例如课程"第六节-第八节"只与排班"第8节"相交，排班"第9、10节"被判为空闲，于是**在学生上课时间排班**（用户实测反馈）。
   *决策*：① 排班表的上班节次编号**与课程表对齐**（默认上午 1~4、下午 6~9），并迁移存量配置中的旧默认值 [1-4]+[8-11] → [1-4]+[6-9]（只迁移与旧默认完全一致的区间，不误改管理员自定义节次）；② 课程占用判定改为**统一换算到"节次序号"后比较**，序号轴集中定义于 `src/utils/sectionOrder.ts`（`SECTION_SEQUENCE`），解析器与算法共用同一换算，消除两份重复的中文节号映射；③ 命名节次（中课1=6、中课2=7、晚课=13）按其真实序号参与占用计算，不再一律按"整天占用"处理——原保守做法会把有午间/晚间课的学生**整天**排除在排班之外，是另一个方向的缺陷；④ 节次原文无法识别时仍退化为整天占用（宁可少排，不在课上排班）。
   *代价与边界*：`CourseInput` 由传数字节号改为传节次原文（算法内部换算），`course` 表结构未变、无需回填；`duty_schedule` 升至 version 3 处理（见下）。回归夹具 `regression-3assistants.json` 用三份真实课程表重建（补充节次原文、下午节次改为 6~9），并移除了无人引用且含旧节次键的历史快照字段 `week1`。
   *v3 迁移为何"归档 + 清空"而不是平移键*（由实测故障驱动）：最初实现为逐行平移（c8→c6、c9→c7、c10→c8、c11→c9），在真实库上直接抛 `ConstraintError: Unable to add key to index '[weekNo+dayOfWeek+timeSlot+assistantId]'`。两个独立原因——① 库中曾同时存在旧标签行与新标签行（中间版本按新编号写过排班），平移会在复合唯一索引上撞键，使**整个升级事务回滚、数据库不可用**（用户导入课程表时报此错）；② 更根本的是**键在两套编号下语义不同**（c8 旧=下午第一节、新=下午第三节），逐行平移会把下午节次**静默改错**，正是本次要修的缺陷类型。由于排班是 (课程表, 规则) 的纯函数结果、可由"生成排班"完整重算，最终改为：把旧排班归档进 `schedule_snapshot`（保留证据）并记一条 `schedule.migrate` 操作日志，然后清空 `duty_schedule` 交由重新生成。该决策与 v2 时段键格式变更时的清空策略保持一致，**不猜测、不撞键、有留痕**。
   *实测效果*：修正后第 1 周自然覆盖全部 5 个工作日（旧编号下"周五无人"本质是该错配的产物）；每日均衡规则在其余周次继续减少"整天无人"（全周期空白天次 13 → 3，未满足时段 401 → 378）。

6. **按助理个性化值班节数（2026-09-13 增补）**：新增需求——可为单个/多个助理单独设置值班节数上下限，覆盖全局默认；未设置者沿用全局。实现：`Assistant` 档案新增可选字段 `customMinSections` / `customMaxSections`（**非索引字段，无需数据库版本升级**），`AssistantInput` 增加 `minSections` / `maxSections`，算法内以 `minSectionsOf` / `maxSectionsOf` 统一解析（undefined → 跟随全局），覆盖主分配、keep 预占、最少工时修复与汇总四处；`AssistantSummary` 增加 `minSections` / `maxSections` 供界面展示"目标区间"。配套：`assistantRepo.update` 改为"读取-合并-写回"（patch 中值为 undefined 的字段会被**删除**），否则"关闭个性化"后旧覆盖值残留继续生效；新增 `validateAssistantOverrides`（最少 ≤ 最多、非负、上限 ≥ 1），与规则校验同一入口把关。
