1. 这个项目是什么

学院行政办公室每学期要给几十名学生助理排值班表。手工排要避开每个人的上课时间、兼顾人数和工时公平，非常繁琐。本系统把它自动化：

导入学生课表(Excel) → 一键生成 17 周值班方案 → 手动微调 → 写入 → 导出带格式的 Excel 排班表
                                                              ↘ 备份/换机交接（一个 JSON 文件）

它是 Windows 离线桌面应用：没有服务器、没有账号、不联网——所有数据存在本机浏览器的 IndexedDB 数据库里，由 Tauri 把网页"装进"一个桌面窗口。

5. 六大业务流程逐条跟代码

5.1 导入一份课表（原子性 + 自动归档）

文件：src/views/CoursesView.vue → src/db/importService.ts → src/utils/courseParser.ts

选文件 → parseTimetableWorkbook(字节, 模板锚点)     ← 纯解析：合并单元格展开、周次"5-17周单周"解析
      → importTimetableForStudent(解析结果)          ← 一个数据库事务：
          ① 按学号查助理：有→更新姓名/身份（保留电话QQ）；无→新建
          ② replaceForAssistant：整体替换该生全部课程（重复导入=幂等）
          ③ deriveImportStatus：推导课表状态（空课表=确认无课；有无法识别节次=待核对）
          ④ 写操作日志 ⑤ dataRevision+1
      → findDutyConflicts / findDutyNeedsReview      ← 影响分析：新课程与已写入排班的冲突/待核对清单

为什么要一个事务包住①~⑤：中途失败（如课程写入出错）会留下"建了助理却没有课表"的半成品。Dexie 事务里任何一步抛错，全部回滚——这在测试里用"故意让某一步抛异常"验证过（故障注入）。

解析器要点（courseParser.ts，22 个测试）：学院课表是合并单元格的网格，先定位表头行（锚点"节次/星期"，可被导入模板配置），再把合并区域按左上角值展开，逐格拆"（本）课程号-课程名[班次] + 周次"。识别不了的节次不丢弃——标记为问题，导入后该生状态变"待核对"。

5.2 自动排班：贪心算法（src/algorithms/greedy.ts）

一次生成 17 周（scheduleAll），每周独立跑 scheduleOneWeek，五个阶段：

① 建时段表     工作日 × 上班节次 → 每节一格（key=c{节号}）
② 算课程占用   每人的课换算到"节次序号轴"（见 6.2），有课的格标忙
③ keep 预占    锁定项先入座——但必须先过安全校验（有课/超容量/超个人上限 → 拒绝+原因）
④ 主分配       时段按"候选人数少的先排"（先难后易）；时段内候选按策略排序（见 5.2.1）
⑤ 收尾         修复⇄撤销迭代（低于下限的补位；孤立短段撤销后再补，最多 4 轮）
               → 每日均衡（消除"某天无人"：新建块/搬移整块，只动纯自动块）
               → 终态清理（P08 教训：最后再撤销一次孤立短段，宁缺勿违规）

5.2.1 候选策略（types.ts candidateStrategy，配置页可选）——只改排序维度先后，不碰任何约束检查：

策略排序
default延续已有连续块 → 已排节数少 → 空闲稀缺 → id
scarceFree 稀缺空闲优先空闲少的人先拿安排
identityFirst 身份优先本科生先于研究生
roundRobin 轮换优先已排最少者优先（严格轮流）

5.3 手动调整与撤销（src/db/manualAdjustService.ts）

点排班表格子 → ManualAdjustDialog。每次操作（增/删/移/锁定/例外登记）：

1. 收集整周当前数据 → toEvaluation() 转成评价器输入
2. 心算"改完后的整周" → evaluateSchedule() 独立复算
3. diffViolations(改前, 改后)——只有【新增】的硬违规才拒绝（改前就有的旧问题不背锅）
4. 拒绝时给出人话原因："星期1 c1 该生有课：「操作系统」（第一节-第二节）"
5. 通过 → 写入 + 撤销日志（同一事务） + dataRevision+1

撤销为什么是日志不是快照：每个操作记录"逆操作所需信息"（新增记整行；移动记来回两个位置）。撤销 = 在新事务里执行逆操作并再过一次第 3 步校验——如果这期间课程变了、撤销回去会撞新课，这次撤销被拒绝。快照式 undo 做不到这个。

CAS（乐观锁）：所有写操作带 expectedRevision（界面上次看到的版本号）。事务里先比对 config.dataRevision，不一致 → StaleDataError"数据已被其他窗口修改"。两个浏览器窗口同时改同一格，后保存的那个会被拦下——测试里用两条真实数据库连接验证过恰好一个成功。

5.4 增量重排（src/algorithms/incremental.ts）

对比全量重排（推倒重来），增量以已写入方案为基准：

  • 输入没变（dataRevision == scheduleWriteRevision，可验证）且基准合法 → 零改动：原样返回，连算都不算；
  • 输入变了 → 把基准行全部作为 keep 传给贪心（锁定的来源记 manual，自动的仍记 auto）；违法的（新课程撞上）被第③步预占校验拒绝并带原因 → 只有被迫的地方变化；
  • 范围外周直接原样输出；
  • 差异按（周，星期，时段，人）输出 保留/新增/移除/替换 + 原因——原因来自拒绝明细等可验证信息，不编造因果。

5.5 导出与隐私（src/utils/scheduleExport.ts）

单周/多周（每周一个 sheet）/快照（用快照里固化的姓名与规则）三种导出。三条隐私红线由测试逐单元格扫描保证：

  1. 永不写学号/QQ（导出输入根本没有这两个字段——结构上不可能泄）；
  2. 电话开关关闭后，所有 sheet 零电话（不只是主表）；
  3. 全部单元格是文本类型——即使有人姓名叫 =SUM(A1) 也不会变成公式。

5.6 备份与恢复（src/db/backupService.ts）

备份 = 跨表只读事务拿一致快照 → 序列化成一个 JSON（含内容摘要，只用于检错）
恢复 = 五道校验（JSON？版本不高于本程序？摘要对得上？学号/排班键唯一？引用的人都存在？）
     → 界面确认数量 → 当前数据先存 recovery_backup 独立表 → 单事务整体替换 → 重数一遍记录数

换机 = 新机器装应用 → 数据管理页导入这个 JSON。失败（比如文件被改坏）原数据分毫不动。

6. 三个值得学会的设计思想

6.1 独立评价器：不信求解器的自述

src/algorithms/evaluate.ts 是全项目最重要的一块。生成、手调、撤销、恢复、增量——每个会产出/修改排班的路径，最后都由它复算一遍：硬违规（课程冲突/超容量/连续段破坏…）存在则不许落库；软缺口（人数不足/低于下限）如实报告但不掩盖。

为什么？项目历史上有个真实教训（审计 P08）：算法的"修复轮"会把孤立的 1 节值班塞回去凑数，而当时的测试只检查第 1 周——缺陷藏在第 3/10/11/12 周。评价器写完当天就把它抓了出来。教训：任何"生产者自己说合法"的系统都需要一个独立的终审。

6.2 节次序号轴：领域错配的根治（src/utils/sectionOrder.ts）

学院课表的节次不是纯数字：1,2,3,4,5,中课1,中课2,6,7,8,9,10,晚课,11,12,13。旧版把排班表下午编成 8~11，与课表的 6~9 错位——同一节课两边编号不同，算法漏判，把人排进了上课时间。修复：建立唯一"序号轴"（中课1=第6个…），课程区间与排班时段都在这个轴上比较；且连续段不跨午休（上午最后一节与下午第一节不算连续）。

教训：两个子系统交换"同一概念"时，先统一坐标系。

6.3 版本号 CAS：无锁的并发安全

没有服务器，怎么防两个窗口互相覆盖？借数据库乐观锁的思想：config 表存一个只增不减的 dataRevision；每个写事务开头校验"我看到的版本还是当前版本吗"，结尾版本+1。同版本的两个写入，后到的在事务里发现版本已变，拒绝并提示刷新。不需要锁，因为冲突在提交时才被检测。

CRSM 业务术语

本文件统一学院行政办助理排班的业务用语。标有“规划”的词条描述本次完善计划中的目标业务概念，不表示当前版本已经实现。

本轮方案与数据交接

当前排班（规划）：用户当前保存、用于日常查看和导出的排班安排。

方案预览（规划）：尚未替换当前排班的候选安排，可以比较、修改或舍弃。

命名快照（规划）：用户固定保存的一份排班及其当时的规则、人员显示信息和输入依据，用于历史查看、对比、导出与受控恢复。

_Avoid_：在线发布版本。

完整备份（规划）：能够恢复助理、课程、规则、安排及相关记录的一份业务数据副本，不等同于用于分发的排班表。

数据交接（规划）：通过备份或业务文件把资料转移到另一台电脑；交接后两台电脑的数据副本独立存在。

_Avoid_：实时同步。

人员与时间

助理：参加行政办值班的学生，具有学生身份、联系方式和课程安排；不是登录账号的同义词。

_Avoid_：用户、账号。

当期参与记录（规划）：一名助理在一个学期内参加排班的资格、状态及个人值班要求。

_Avoid_：永久工时配置、跨学期名单。

学期（规划）：一段具有确定教学日历的教学周期，是课程、排班规则和排班结果的归属范围。

排班周期：一次生成方案所覆盖的周次范围；可以是一个学期的全部或部分周次。

_Avoid_：每周工时周期。

周次：某一天或某项安排在所属学期教学日历中的周序号。

节次：学院课程表中可辨认的教学时段，包括数字节次、中课和晚课。

_Avoid_：节次序号。

节次序号：所有节次在一天内按实际先后排列的位置；数字节次的号码不一定等于该位置。

_Avoid_：节号。

值班节数：分配给助理的值班量，以排班节次计数。现有算法的个人上下限实际按每周分别计算。

_Avoid_：小时数、全周期累计工时。

约束与求解

课程占用：一名助理在有效周次、星期和节次上因课程而不可值班的状态。

连续值班段：同一助理在同一天、同一工作区段内实际连续的一组值班节次。

_Avoid_：数字节号相邻。

覆盖缺口：某一排班时段实际值班人数低于要求下限的差额。

_Avoid_：硬约束冲突。

手动安排：由排班老师指定的人与时段关系，表示安排的来源。

_Avoid_：锁定项。

锁定项（规划）：在明确周次和时段上要求求解过程保持不变的安排；锁定不能使课程冲突等不可豁免条件变为合法。

_Avoid_：所有手动安排、全周期保留项。

增量重排：以已有方案为基准，保留有效锁定并优先减少变动，对受输入变化影响的安排重新计算。

_Avoid_：直接覆盖全部旧排班。

方案与协作（规划）

排班方案：针对确定学期和排班周期的一套候选工作安排。

排班草稿：尚未发布、可在权限和校验约束下编辑的候选安排。

输入快照：生成某个方案时实际采用的课程、人员资格、规则、节次和可用性条件的固定集合。

_Avoid_：当前实时配置。

发布版本：正式对助理生效的一次完整排班修订；发布后作为历史依据保留。

_Avoid_：可直接覆盖的当前表。

新修订：基于已有方案产生的后续候选或正式安排，不改变原发布版本的历史含义。

调班申请：助理请求改变已发布值班安排的业务请求；提交申请本身不使新安排生效。

_Avoid_：直接修改已发布排班。

排错手册（troubleshooting）

按步骤书 0.3 节，项目中有价值的坑位记录于此。格式：现象 → 根因 → 解决 → 教训。

T-001 字体安装后 VS Code 不生效

  • 现象：按 JetBrains Mono 扩展的字体包设置 editor.fontFamily，编辑器字体不变。
  • 根因：用命令行注册用户字体时路径拼接少了一个反斜杠（...\Windows\FontsJetBrainsMono-Regular.ttf），字体从未真正注册，VS Code 静默回退到备选字体 Consolas，无任何报错。
  • 解决：清理错误注册表项（HKCU\...\Fonts 下 JetBrains Mono *），用 PowerShell 脚本以 Join-Path 拼路径重新复制+注册，并调用 AddFontResource + 广播 WM_FONTCHANGE；随后完全退出 VS Code 再启动（Electron 进程只在启动时枚举字体，Reload Window 不够）。
  • 教训：① 字体"静默回退"不报错，排查必须查 GDI 注册结果而不是只看配置；② 跨 shell 拼 Windows 路径时用脚本文件而不是内联命令，避免多层转义；③ 用户字体注册在 HKCU，系统级在 HKLM，前者无需管理员。

T-002 Rust 侧重命名需要三处同步

  • 现象：把脚手架 scaffold-tmp 改名为 crsm 时，若只改 Cargo.toml 的 package name，main.rs 里的 scaffold_tmp_lib::run() 编译报"找不到 crate"。
  • 根因：Tauri 项目 Cargo.toml 中 [lib] name（如 crsm_lib）与 main.rs 的调用点、tauri.conf.json 的 productName/identifier 是三组独立标识。
  • 解决：package/lib name、lib 调用、productName（安装包名）、identifier（应用唯一 ID）、窗口标题全部同步改。
  • 教训：Rust 编译器会拦住不一致，所以这类问题必现必报——比前端"静默 undefined"友好；改名后先 cargo check 再继续。

T-003 Vue 模板模板编译错误的定位方式

  • 现象：npm run build 失败在 vue-tsc 阶段，报错行号指向编译产物。
  • 解决：先单独跑 npx vue-tsc --noEmit 拿到 .vue 源文件级别的报错行号，再修；不要直接读 vite 打包日志。
  • 教训：前端构建链分"类型检查（vue-tsc）→ 转译打包（vite）"两层，分别排查。

T-004 Dexie delete() 后实例不会自动重开

  • 现象：单测 beforeEach 中 await db.delete() 后，首个数据库操作抛 DatabaseClosedError: Database has been closed，全部用例连挂。
  • 根因：原以为 Dexie 实例在 delete 后的下次操作会自动重开（autoOpen），实测（fake-indexeddb 环境，探针验证）delete 后实例保持 closed，autoOpen 不触发。
  • 解决：await db.delete() 之后显式 await db.open()。
  • 教训：对库的行为假设要用最小探针验证（10 行代码），而不是凭印象写 12 个用例再全挂；探针法把 30 分钟排查压缩成 1 次 15ms 的运行。

T-005 管道吞掉命令退出码，带病提交

  • 现象：npm run build | tail -3 && git commit 在构建失败（TS6196 未使用类型）时依然执行了提交。
  • 根因：bash 管道的退出码默认取最后一个命令（tail 总是成功），&& 判断失真。
  • 解决：验证类命令要么单独跑，要么 set -o pipefail；提交前以"重新单独运行验证"为准。
  • 教训：自动化脚本里，命令 | 美化输出 && 后续动作 是经典陷阱；验证与提交必须解耦。

T-006 弹窗表单残留上次数据（watch prop 失效）

  • 现象：GUI 走查发现，连续两次打开"新增助理"弹窗，第二次的表单里残留上一次填写（或编辑）的手机号、班级。
  • 根因：表单初始化写在 watch(() => props.assistant) 里。连续新增时该 prop 一直是 null，引用未变 → watch 不触发 → 表单不复位。
  • 解决：改为 watch(visible)（监听弹窗打开动作）在打开瞬间按 props.assistant 重置表单，并 clearValidate() 清除上次校验痕迹。
  • 教训：watch 依赖的是"值的变化"，null → null 不算变化；"打开容器"这类事件语义的状态（布尔量）才是正确的触发源。父组件必须保证先改 assistant 再改 visible。

T-007 GUI 自动化中的"僵尸页面"：HMR 与浏览器缓存的混合劣化

  • 现象：开发服务器多次 HMR 后，浏览器内自动化（IAB）出现大面积诡异：Playwright 点击全部 actionability 超时、CUA 键盘事件（Enter/Ctrl+F5）不到达、截图失败、按钮原生 .click() 后 Vue 处理函数不执行、页面运行的模块版本落后于服务端。
  • 根因：长时间会话中 HMR 多次热替换 + guest 页面缓存，导致"服务端代码 / 页面运行代码 / 输入事件通道"三方不一致。表现为任何单一角度的排查都自相矛盾（编辑按钮好用、删除按钮不好用）。
  • 解决：完全重启 Vite（注意 git-bash 的 kill 杀不掉 Windows 进程，要用 taskkill //F //PID）→ 浏览器新开标签页 → 加临时 console.log 探针确认运行的代码版本 → 全绿。
  • 教训：① 排查"灵异问题"前先确认三方版本一致（服务器/页面/事件通道）；② console.log 探针是判定"代码版本"的最快手段；③ git-bash 下杀 Windows 进程用 taskkill；④ 将 ElMessageBox（命令式服务）替换为声明式 el-dialog 后，确认框行为一致且在该环境下可测——命令式服务在自动化环境中更脆弱。

T-008 响应式 Proxy 对象写入 IndexedDB 抛 DataCloneError

  • 现象：导入课程确认入库时报 Failed to execute 'add' on 'IDBObjectStore': [object Array] could not be cloned。
  • 根因：解析结果存入 Vue ref 后变成响应式 Proxy（深层），IndexedDB 的 structuredClone 不能克隆 Proxy 对象。spread 展开（{...c}）只是浅拷贝，嵌套的 weekRanges 仍是 Proxy。
  • 解决：在数据落库边界逐字段构造纯对象（含把嵌套数组显式重建），或用 Vue 的 toRaw() 后深拷贝。
  • 教训：① "Vue 状态 ≠ 纯数据"——跨出响应式系统的边界（IndexedDB、fetch body、Web Worker postMessage）必须先脱壳；② 这类错误只在运行时暴露，把落库操作放在仓储层并配集成测试才能尽早拦截。

T-009 两套节次编号不一致导致"在上课时间排班"

  • 现象：排班结果把助理排在了他有课的时间段里。用户从界面上发现"导入的课程表和排班表的节次显示不一致"：课程表里下午刚开始的两节课是"第6节、第7节"，而排班表把它们标为"第8节、第9节"。
  • 根因：同一节真实课程在两处编号不同。实测课程表 A 列时段块得到全天的节次序列是"数字节次 + 命名节次"混排：上午 1~5、中课1/中课2、下午 6~10、晚课、晚上 11~13；而排班表的上班节次默认写成"上午 1~4、下午 8~11"。占用判定原本直接比较节号区间，于是课程"第六节-第八节"（真实占下午前三节）只会与排班"第8节"相交，排班"第9、10节"被判定为空闲 → 在这些节次上排班，正好落在课前两节里。更隐蔽的是：因为偏移是 2 而不是"整体错位"，判定结果是"部分相交"，既不会报错也不易被察觉，只会表现为局部错排。
  • 解决：① 排班表上班节次编号改为与课程表一致（上午 1~4、下午 6~9）；② 占用判定不再比较节号，而是先统一换算到"当日先后序号"再比较，序号轴集中定义在 src/utils/sectionOrder.ts（SECTION_SEQUENCE），解析器与算法共用同一换算；③ 迁移存量：normalizeRules 把旧默认 [1-4]+[8-11] 对齐为 [1-4]+[6-9]（只迁移与旧默认完全一致的区间），数据库升到 version 3 把 duty_schedule.timeSlot 的 c8~c11 就地平移为 c6~c9；④ 回归夹具用三份真实课程表重建，补齐节次原文。
  • 教训：① 同一实体在两处被各自编码，就必须建立显式的换算层——只要比较的是"编号"而不是"含义"，错配就只是时间问题；② 偏移型错配比整体错位更危险，因为它产生"部分正确"的结果，测试若只覆盖粗粒度场景（如"有课就不排"）很容易漏过；③ "非数字标签一律保守按整天占用"这类兜底虽然安全，但会掩盖真实结构——先花时间把数据摸清（本次靠 A 列时段块 7 个标签就把序列还原出来了），再决定是精确计算还是保守退化；④ 遇到"用户说 A 表和 B 表对不上"的反馈，先做同一份数据在两处的对照样例，比读代码猜更快。

T-010 版本升级里"平移索引键"引发 ConstraintError，整库不可用

  • 现象：导入课程表时报 Error modifying one or more objects. Errors: ConstraintError: Unable to add key to index '[weekNo+dayOfWeek+timeSlot+assistantId]': at least one key does not satisfy the uniqueness requirements. 报错发生在"导入"动作上，看起来像导入逻辑的 bug。
  • 根因：报错根本不在导入路径上。Error modifying one or more objects 是 Dexie 升级事务里 Collection.modify() 的固定措辞，而那个索引属于 duty_schedule 表。真实链路是：页面首次访问数据库 → Dexie 执行 v3 升级（把下午节次键从 8~11 平移为 6~9）→ 库中同时存在旧标签行与新标签行（先前的中间版本已按新编号写过排班）→ c8→c6 撞上已有的 c6 行 → 复合唯一索引报错 → 整个升级事务回滚，数据库版本不提升且保持不可用，于是任何写操作（第一个动作恰好是导入）都失败。导入本身完全无辜。

更深一层：这个"平移"从语义上就不成立——同一个键在两套编号下含义不同（c8 旧=下午第一节、新=下午第三节），逐行平移即使不撞键也会把下午节次静默改错。

  • 解决：① 先修"何时升级"——不要在界面已按新编号写入数据之后才补迁移；编号相关的改动要把默认值、算法、持久化迁移作为一次原子变更一起发布。② 迁移本身改为不猜测：把旧排班归档进 schedule_snapshot（留痕）并记一条 schedule.migrate 日志，然后清空 duty_schedule，由"生成排班"按 (课程表, 规则) 重算——排班是纯函数结果，可完整重建，与 v2 时段键格式变更时的清空策略一致。③ 补 src/db/migration.test.ts：用一个"只声明到 version 2"的 Dexie 实例伪造旧库（含旧新标签并存的混合态）再触发真实升级，锁定"不抛错 + 归档 + 清空 + 其他表保留"。
  • 教训：① 唯一索引 + 键重映射 = 事务级炸弹：单行合法、批量非法，失败点还不在调用方以为的地方；凡是升级里要改带唯一约束的键，必须先按"最终键"整体规划并去重，而不是就地逐行改。② 键当且仅当语义稳定时才可以重用：同一编号在不同版本下换了含义，就应视为新键，旧的必须显式迁移或废弃。③ 用户报"某个按钮出错"时，先看错误措辞属于哪一层（这里是 Dexie 升级事务，而非业务代码），再决定排查方向——否则会在导入逻辑里白找很久。④ 伪造旧版本库来测试迁移，比在真实库上试错安全得多。

T-011 删除实体只清理了"直接附属"，漏了"派生引用"

  • 现象：删除一名助理后，排班表与导出文件里出现 #7 这样的条目（本应是姓名）。
  • 根因：assistantRepo.remove 的事务里只级联删除了 course（直接附属数据），漏掉了 duty_schedule（引用该助理的派生数据）。IndexedDB 没有外键约束，引用完整性完全靠应用层自觉。
  • 解决：事务扩到三张表，按 assistantId 一并删除排班记录；并用"删除后他人排班保留、本人排班清零"的用例锁死。
  • 教训：① 删除一个实体前，先列出所有含其外键的表，逐一对账——无外键约束的存储（IndexedDB/localStorage/文档库）尤其如此；② "级联删除"应该是一个完整清单而不是"想到哪写到哪"。

T-012 派生视图按"当前配置"渲染，会和历史数据脱节

  • 现象：已写入排班（上午 1~2 节）后，把上班节次改成"下午 6~9 节"，再看排班表/导出文件——数据还在库里，但表格里所有格子都是 —，像是被清空了。
  • 根因：网格/导出的行与列完全由当前规则推导，而数据行存的是写入当时的节次键。配置一变，视图与数据的坐标系就不再对齐。用户改配置后直接导出，交出去的是一张空表。
  • 解决：行列骨架改为「当前规则 ∪ 已写入数据」的并集（src/utils/scheduleGrid.ts）——规则内的节次照常带时间标注，数据里多出来的节次也会显示（只显示节号/无时间标注的写法），任何已写入数据都可见；排班表页面与导出模块共用同一推导，避免两处口径再漂移。
  • 教训：① 凡是"视图按配置推导、数据按历史快照存储"的组合，都要问一句：配置变了之后，旧数据还能不能被看见？② 用并集而不是"以配置为准"或"以数据为准"，是因为两者各有正确的场景（空表需要配置行、旧数据需要数据行）；③ 该修复顺带消除了"网格列顺序依赖对象整型键升序"的脆弱写法（改为显式传入天数组、按键取值）。

T-013 xlsx 脱敏：跨文本 run 的敏感串替换会漏改，且整串检测查不出来

  • 现象：对课程表做个人信息脱敏时，按"文本片段"做子串替换后，残留检测显示"无残留"，但打开文件发现学号仍在（如 学生：示例学生A(10240052 后面还跟着 54)）。
  • 根因：OOXML 中同一单元格的文本可以按字体/字符集被 Excel 拆成多个 <t> run。实测三份课表中，两份的表头被拆成三段：

学生：示例学生A(20260000 + 01 + )　　——目标串 2026000001 在任何单个 run 中都不完整存在，因此替换命中不了；而残留检测若按原始字节查找整串，同样查不到，形成假阴性。第三份文件恰为单 run，顺利替换，反而掩盖了问题。

  • 解决：改为按单元格（<si>）处理——拼接该单元格全部 run 文本 → 做整体替换 → 按原 run 长度重新切分回填（run 数与各 run 的 <rPr> 样式得以保留，仅文本位移）。残留检测同步改为基于"拼接后的单元格文本"，并补充"10 位学号式数字"扫描，防止同类漏网。
  • 教训：① 凡对 OOXML 文本做查找替换，必须以单元格为单位，不要把解析粒度等同于文本 run；② 负向断言（"文件里不该有 X"）在替换前就要设计好检测方法，否则"替换失败 + 检测漏报"会同时发生，让人以为已经干净；③ 样本里只要有一份文件"侥幸通过"，就必须对全部样本逐一验证，而不是抽样；④ 脱敏必须覆盖三层——表头姓名学号、上课教师 字段、以及 docProps/core.xml 的 cp:lastModifiedBy 元数据（元数据里存着制作人真名，是最容易漏的一层）；⑤ 结构完整性可用"仅 sharedStrings.xml 与 core.xml 变化、其余部件字节级一致、合并单元格数量不变"作为判据。

T-014 批量替换版本号误伤 Cargo.lock 中的同名第三方依赖

  • 现象：执行"把项目版本从 1.0.0 改为 0.1.0"的批量文本替换后，git diff 显示 src-tauri/Cargo.lock 有两处改动，而本项目的包只有一个。
  • 根因：Cargo.lock 是所有依赖的版本清单，其中 defmt-parser 恰好也发布过 1.0.0，被无差别替换成 0.1.0。锁文件一旦被改坏，cargo 会认为锁定版本与 registry 不符，轻则报错、重则静默重写锁文件造成依赖漂移。
  • 解决：替换锚点必须是包名 + 版本的组合（name = "crsm"\nversion = "1.0.0"）而非孤立的版本字符串；替换后立即用 git diff 核对改变行数（本次应为 1 行），并用 cargo metadata --no-deps --offline 验证锁文件仍可解析。其他文件同理：package.json 的 version 字段唯一，但 package-lock.json 同样包含大量依赖版本（如 "@types/estree": "^1.0.0"），需按缩进/上下文精确匹配。
  • 教训：① 锁定文件与清单文件里的"版本"不是同一个概念——前者是依赖矩阵，后者是自身版本，批量替换前必须先分清；② 任何批量替换都要先看命中了多少处，命中数超出预期就停下来核对，而不是直接写回；③ 版本号这类"元信息"改动最好用脚本 + 断言（期望命中次数），把"改对了几处"变成可验证的检查项；④ 项目版本号需同步的位置固定为六处：package.json、package-lock.json（两处 version 字段）、src-tauri/Cargo.toml、src-tauri/Cargo.lock（crsm 条目）、src-tauri/tauri.conf.json、src/meta.ts（界面展示 v0.1），外加 README.md 与 CHANGELOG.md 的文档描述。

T-015 每日均衡阶段误用全局上限，突破"个性化值班节数"

  • 现象：给某助理设置了较小的"个性化值班节数上限"（如 1 节），最终排班却给他排了 3 节，超出其上限。汇总表里 实际 > 上限，属静默产出错误结果。
  • 根因：算法里"每人工时上限"的解析被收敛到 maxSectionsOf(a)（个性化覆盖优先），主分配、keep 预占、工时修复、汇总共 4 处都用了它；唯独"每日均衡"阶段新建连续块时仍写死 rules.maxSectionsPerAssistant，于是用全局上限算出的"剩余额度"成了实际闸门。之所以能一路通过，是因为该阶段唯一的守卫 canPlaceBlock 只校验节次存在、课程占用与同时段人数上限，不校验工时——缺口正好落在这里。
  • 解决：改为 maxSectionsOf(a)；补注释点明"此处是本阶段唯一的工时闸门"；新增两条用例锁定——① 全局 3 / 个人 1 时必须只排 1 节（修复前实测 3 节）；② 反向保护：个人上限大于全局时仍能突破全局值，防止"把上限一律夹到全局值"的过度纠正。同时把 checkInvariants 的口径从全局上限改为生效上限（s.maxSections），否则不变量校验本身与个性化语义矛盾。
  • 教训：① "同一规则多处实现"是这类缺陷的唯一温床——本次正确的解析散落在 4 处、错误的一处却逃过了所有既有用例；引入个性化覆盖这类"同字段多种取值来源"的需求时，应当先找出该字段的全部读取点再动手，而不是改到哪算哪。② 守卫函数的职责边界要写清：canPlaceBlock 名字像"能不能放"的完整判定，实际不含工时限，这种"名字比行为更宽"的函数最容易被误当作兜底。③ 回归测试必须先证明它能捕获缺陷（本次先在未修代码上跑出 8 例越限）——否则很容易写出"写了就通过"的空洞用例；本次第一版探针容量充足、根本没触发均衡路径，属空洞用例，靠打印的触发计数才发现。

二、数据存储方案

2.1 方案A：localStorage

描述：利用浏览器内置的 localStorage API 存储键值对数据。

优点：

  • 零配置，API 简单（setItem / getItem）
  • 同步读写，开发门槛低
  • 无需额外依赖库

缺点：

  • 容量限制严格（通常 5MB 以下）
  • 仅支持字符串存储，复杂数据结构需手动序列化
  • 无法建立索引，查询性能随数据量增长急剧下降
  • 不适合存储结构化表格数据（如课程表、排班表）

适用场景：系统配置、用户偏好等小量简单数据。

2.2 方案B：IndexedDB（已采纳）

描述：浏览器内置的结构化数据库，支持存储对象、数组等复杂数据结构，支持索引和事务。

优点：

  • 容量大（无硬性上限，通常数百MB起步）
  • 支持结构化数据查询（类似数据库的索引和事务）
  • 异步操作，不阻塞主线程
  • 数据持久化，关闭应用后数据不丢失
  • 可通过封装库（如 Dexie.js）简化 API 调用

缺点：

  • 原生 API 较复杂（回调地狱），需封装库降低使用门槛
  • 不支持 SQL 查询，复杂关联查询需应用层实现
  • 数据孤岛，不同设备间不互通

封装库选择：

库名特点选择理由
Dexie.js基于 IndexedDB 的 Promise 封装，API 简洁，支持表定义和索引推荐，学习成本低，文档完善
localForagelocalStorage 的异步封装，API 极简功能较单一，不适合复杂查询场景

最终选择：IndexedDB + Dexie.js

2.3 方案C：后端数据库（SQLite / MySQL）

描述：搭建后端 API 服务 + 关系型数据库，采用前端→后端→数据库的三层架构。

优点：

  • 数据持久化且安全，不依赖浏览器
  • 支持多端同步和多人协作
  • 数据完整性有保障（事务、约束、索引）
  • 可扩展性强

缺点：

  • 需要搭建后端服务（Flask/FastAPI/Express），开发成本高
  • 需要服务器环境部署，不符合本项目"无服务器"约束
  • 学习曲线陡，需掌握后端框架、数据库 SQL、API 设计等

最终选择：不采用。本项目为课程简易项目，无服务器环境，不满足多端协作需求，采用此方案过度设计。

三、应用打包方案

3.1 方案A：Electron 打包

描述：使用 Electron 框架将 Web 技术（HTML/CSS/JS）打包为桌面应用程序。

优点：

  • 生态成熟，社区资源丰富，教程多
  • 拥有完整的 Node.js 能力，可自由访问本地文件系统
  • 打包产物为独立 .exe（Windows）/ .dmg（Mac），用户体验好
  • 支持文件对话框、系统通知等桌面能力

缺点：

  • 打包体积大（约 80-150MB），因为捆绑了 Chromium 浏览器引擎
  • 内存占用较高
  • 启动速度相对较慢

打包产物：一个 .exe 安装包，双击安装后在桌面生成快捷方式。

3.2 方案B：Tauri 打包（已采纳）

描述：使用 Tauri 框架，前端用 Web 技术编写，后端用 Rust 实现，调用系统自带的 WebView2 渲染页面。

优点：

  • 打包体积极小（约 3-10MB），不捆绑浏览器引擎
  • 内存占用低，性能优秀
  • 调用系统自带 WebView2（Windows 10/11 自带），无需额外安装浏览器
  • 同样支持本地文件读写，导入导出功能完整
  • Rust 后端提供内存安全保证

缺点：

  • 需要用户系统为 Windows 10 以上（Tauri v2 依赖 WebView2）
  • 社区生态相比 Electron 较小，部分插件可能不兼容
  • 学习曲线稍陡（需了解 Rust 基础概念）

打包产物：一个轻量级 .exe 安装包（约 3-10MB），双击即可运行。

最终选择：Tauri

选择理由：本项目为课程项目，打包体积小更便于分发和提交作业；性能足够满足排班系统的功能需求；Rust 后端的学习本身也是软件工程课程的良好实践。

3.3 方案C：直接双击 HTML 文件

描述：不打包，直接将 .html 文件双击用系统默认浏览器打开使用。

优点：

  • 零打包，开发调试最直接
  • 无需安装任何运行时环境

缺点：

  • 现代浏览器对 file:// 协议有严格的安全限制
  • localStorage 和 IndexedDB 在 file:// 下可能无法正常使用或数据不持久
  • 部分浏览器会阻止本地文件读取操作
  • 用户体验差（地址栏显示文件路径，无独立窗口）

最终选择：不采用。体验不稳定，不满足工程交付标准。

2026-09-13 修订：Excel 库由 SheetJS 社区版切换为 xlsx-js-style。
触发原因：需求要求导出排班表中助理"姓名与电话上下两行显示"，并提升版式美观度。实测确认社区版 SheetJS 无法写入任何单元格样式——其 write_cellXfs 只序列化 numFmtId（get_cell_style 生成的 xf 恒为 fontId/fillId/borderId:0），产物 xl/styles.xml 中既无 alignment 也无 wrapText，工作表单元格也不带 s 属性，因此"上下两行"在 Excel/WPS 中不会生效。
方案对比：① 手工改写 OOXML（解压 xlsx → 注入 styles.xml 与单元格 s 属性 → 重新打包）：需自行实现 zip 读写、deflate 与 CRC32，约 200 行且需在 WebView2 中验证 CompressionStream 可用性，维护风险高；② 使用支持样式写入的库：xlsx-js-style 是 SheetJS 0.18.5 的直系分支，读写 API 完全兼容，仅额外支持 cell.s（字体/边框/对齐/填充），切换到它只需替换 import，课程表解析器等既有读取路径零改动（9 项解析测试原样通过）。
决策：采用方案 ②，并移除原 xlsx 依赖，全项目只保留一个 Excel 库，避免重复打包。代价说明：该分支的 dist 体积大于社区版，共享 chunk 由约 420 KB 增至约 864 KB（gzip 后约 +150 KB）。因本项目为 Tauri 单机桌面应用（本地加载、不走网络），且该 chunk 随路由懒加载、不在首屏关键路径上，此代价可接受。风险 R04（大文件解析性能）结论不变：读取路径与社区版同一实现。

  1. 前端框架在 ADR-001 技术栈表中标记为"Vue 3 / React（待定）"；
  2. SRS 的核心功能 F01（自动排班）未约定具体算法；
  3. SRS 的 F04（撤销/重做）与 F08（重排差异对比）未约定实现机制；
  4. ADR-001 初版数据表缺少 SRS 明确要求的字段（课程周次、学号、排班来源标记），将直接导致空闲时间计算错误与重排功能失效。

三、排班算法选型（SRS F01）

3.1 问题建模

自动排班本质是一个约束满足问题（CSP）：将"助理-时段"视为二分图匹配，约束包括同时段人数上下限、每人工时上下限，目标是生成无冲突且覆盖完整的排班方案。

3.2 候选方案对比

对比维度贪心启发式（已采纳）回溯搜索（CSP）最小费用最大流
基本思路约束最紧的时段优先分配，候选按剩余空闲时间排序，冲突时局部修复系统性搜索 + 剪枝求可行解工时上下限建模为图论费用
时间复杂度O(n×m)，50人×约百时段毫秒级最坏指数级，依赖剪枝质量多项式级，但实现复杂
解的质量非全局最优可行性保证强解质量有理论保证
实现难度低高高
兜底手段F04 手动调整即为设计好的兜底--

3.3 最终选择

贪心启发式。

理由：SRS 4.1 要求 50 人 5 秒内完成排班，贪心算法毫秒级即可满足；解不保证全局最优，但 F04 的手动调整功能本就是流程的一部分，最优性要求可以放宽。升级路径：若后续对解质量有更高要求，可在阶段二引入最小费用最大流替换核心分配器，对外接口不变。

3.4 算法流程约定

  1. 计算每位助理的空闲时间矩阵（课程表取反，按周次过滤）；
  2. 对排班时段按"约束紧度"排序（要求人数多、可用人少的时段优先）；
  3. 对每个时段，从候选人中按剩余可用工时/空闲度排序依次分配，直至满足人数要求；
  4. 全部分配后校验每人工时上下限，违反者触发局部调整（在可交换的时段间调换）；
  5. 输出排班结果及未满足时段清单，交由手动调整处理。

四、撤销/重做机制选型（SRS F04、F08）

4.1 候选方案对比

对比维度快照栈（已采纳）命令模式

快照栈。

理由：数据规模小，快照成本可忽略；实现简单可靠；F08 的"重排前后对比"直接基于快照 diff 实现。快照持久化存储于 IndexedDB 的 schedule_snapshot 表，应用重启后仍可恢复历史。

七、修订记录（2026-09-11，新增需求驱动）

  1. 排班模式：新增"各周排班相同"（uniform）模式——以周期内任一周有课即占用，生成一份方案复制到全部周次；默认"各周独立"。算法 API 由单周 scheduleWeek 调整为 scheduleAll（内部逐周或统一计算）。
  2. 课程占用过滤：Course 表新增 kind 字段（theory/experiment，由样例标记（本）/（实）推导），规则可配置两类课程是否计入占用；数据库升级至 version 2 做存量回填。
  3. 上班时间表：时段不再使用固定模板，由规则中的工作日（默认周一~五）× 上班节次（默认上午 1~4 节、下午 6~9 节）推导；duty_schedule.timeSlot 存节次区间键（如 c1-4），排班表按时段节次显示。
  4. 每日均衡（2026-09-13）：新增规则 balanceDaily（默认 true）。贪心主分配按"时段紧度先难后易"逐时段填人，容量会优先消耗在排序靠前的日子上，可能出现"周一~周四已排妥、周五无人"。因此在收敛结果之上追加每日均衡阶段，判据是"该工作日的每个上班节次都达到人数下限"（下限取 max(1, minPerSlot)，即"某天无人"一律视为不达标）。可用手段分两档：
  • A 档 · 零损伤：① 为助理在该天新建满足最少连续节数的连续块；② 把某助理的整个连续块搬到该天的空闲连续段（块节数不变 ⇒ 工时净变化为 0）。均要求源时段移出后仍满足 minPerSlot（只动用冗余值班），不新增未满足时段。择优选人时以"已值班天数最少者优先"。
  • B 档 · 兜底让位（2026-09-13 追加，由实测反馈驱动）：A 档要求"源时段移出后仍满足人数下限"，在工时上限已用尽的数据上等价于禁止一切搬移——实测三助理夹具（3 人 × 上限 6 节 = 18 人节 vs 40 个时段，且每个已排时段恰好 1 人、冗余数为 0）下，第 1 周周五永远无人。故追加兜底：仅当某工作日一个人都没有且 A 档无解时，允许搬走整个连续块、把源时段的覆盖让出来，从而保证"每天都有人"。硬性闸门：源日让出后仍须有 ≥1 条排班（绝不把空白天转移给别的日期）；择优顺序为损伤最小（跌出人数下限的源时段个数）→ 块最短 → 源日值班最多（从最拥挤的天让出）→ 助理 id（确定性）。
  • 取舍（显式记录）：该夹具下 18 < 40，"每个时段都有人"数学上不可达，"每天都有人"与"每时段都有人"不可兼得。实现显式优先前者（需求核心目标），被让出的时段进入未满足时段清单交由手动调整兜底——这是有意的产品取舍，而非静默破坏约束。实测效果：全周期空白天次 22 → 0、未满足时段 399 → 374（未增加），每人工时与排班总量守恒。
  • *为什么不做"每日人数差最小化"*：各工作日上班节次相同 ⇒ 每日时段数相同，主分配本就会把每个时段填到人数上限，真正的失衡形态就是"某天归零"；而搬移粒度受最少连续节数约束、无法细分到单节微调人数差，强行迭代会在两个状态间来回搬运、永不收敛。故收敛目标锁定为"消除整天无人"。
  • 该阶段不引入新数据结构，也不需要数据库版本升级。
  1. 节次序号轴（2026-09-13，缺陷修复）：实测课程表的节次是"数字节次 + 命名节次"混排的连续序列——上午第 1~5 节、午间"中课1/中课2"、下午第 6~10 节、傍晚"晚课"、晚上第 11~13 节（顺序取自课程表 A 列时段块）。原设计把排班表的下午编为第 8~11 节，而课程表编为第 6~9 节，同一节真实课程在两表中编号相差 2；占用判定按节号比较区间时会漏判——例如课程"第六节-第八节"只与排班"第8节"相交，排班"第9、10节"被判为空闲，于是在学生上课时间排班（用户实测反馈）。

*决策*：① 排班表的上班节次编号与课程表对齐（默认上午 1~4、下午 6~9），并迁移存量配置中的旧默认值 [1-4]+[8-11] → [1-4]+[6-9]（只迁移与旧默认完全一致的区间，不误改管理员自定义节次）；② 课程占用判定改为统一换算到"节次序号"后比较，序号轴集中定义于 src/utils/sectionOrder.ts（SECTION_SEQUENCE），解析器与算法共用同一换算，消除两份重复的中文节号映射；③ 命名节次（中课1=6、中课2=7、晚课=13）按其真实序号参与占用计算，不再一律按"整天占用"处理——原保守做法会把有午间/晚间课的学生整天排除在排班之外，是另一个方向的缺陷；④ 节次原文无法识别时仍退化为整天占用（宁可少排，不在课上排班）。

*代价与边界*：CourseInput 由传数字节号改为传节次原文（算法内部换算），course 表结构未变、无需回填；duty_schedule 升至 version 3 处理（见下）。回归夹具 regression-3assistants.json 用三份真实课程表重建（补充节次原文、下午节次改为 6~9），并移除了无人引用且含旧节次键的历史快照字段 week1。

*v3 迁移为何"归档 + 清空"而不是平移键*（由实测故障驱动）：最初实现为逐行平移（c8→c6、c9→c7、c10→c8、c11→c9），在真实库上直接抛 ConstraintError: Unable to add key to index '[weekNo+dayOfWeek+timeSlot+assistantId]'。两个独立原因——① 库中曾同时存在旧标签行与新标签行（中间版本按新编号写过排班），平移会在复合唯一索引上撞键，使整个升级事务回滚、数据库不可用（用户导入课程表时报此错）；② 更根本的是键在两套编号下语义不同（c8 旧=下午第一节、新=下午第三节），逐行平移会把下午节次静默改错，正是本次要修的缺陷类型。由于排班是 (课程表, 规则) 的纯函数结果、可由"生成排班"完整重算，最终改为：把旧排班归档进 schedule_snapshot（保留证据）并记一条 schedule.migrate 操作日志，然后清空 duty_schedule 交由重新生成。该决策与 v2 时段键格式变更时的清空策略保持一致，不猜测、不撞键、有留痕。

*实测效果*：修正后第 1 周自然覆盖全部 5 个工作日（旧编号下"周五无人"本质是该错配的产物）；每日均衡规则在其余周次继续减少"整天无人"（全周期空白天次 13 → 3，未满足时段 401 → 378）。

  1. 按助理个性化值班节数（2026-09-13 增补）：新增需求——可为单个/多个助理单独设置值班节数上下限，覆盖全局默认；未设置者沿用全局。实现：Assistant 档案新增可选字段 customMinSections / customMaxSections（非索引字段，无需数据库版本升级），AssistantInput 增加 minSections / maxSections，算法内以 minSectionsOf / maxSectionsOf 统一解析（undefined → 跟随全局），覆盖主分配、keep 预占、最少工时修复与汇总四处；AssistantSummary 增加 minSections / maxSections 供界面展示"目标区间"。配套：assistantRepo.update 改为"读取-合并-写回"（patch 中值为 undefined 的字段会被删除），否则"关闭个性化"后旧覆盖值残留继续生效；新增 validateAssistantOverrides（最少 ≤ 最多、非负、上限 ≥ 1），与规则校验同一入口把关。
